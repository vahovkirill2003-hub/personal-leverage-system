2. `docs/01…05-*-v2.md` — продуктовый baseline

## Жёсткие запреты

- НИКОГДА не редактируй файлы в `docs/` — это принятый канон с хешами.
- Не добавляй Redis, Kafka, Kubernetes, Temporal, микросервисы, provider-hosted tools — сознательно исключены (arch §1.3, §12.6.8).
- Не создавай команд вне реестра `docs/17…v0.3.md` §1.2 (43 команды: 24 из v0.1 + 16 доменных команд правил + 3 команды контура восстановления `PLS-073`) — незарегистрированный путь записи не существует.
- Модельный вывод — только proposal: ни один LLM-результат не пишет состояние без валидации `docs/18` §6.
- Никаких реальных персональных данных в фикстурах и тестах — только синтетика (`docs/22` §0.3).
- Секреты не хардкодятся, не логируются, не попадают в фикстуры.

## Порядок работы

- Строго по задачам TB-01…TB-39 (включая TB-04a) из `docs/25…v0.2.md`, по одной, в порядке зависимостей. Не начинай следующую без явного «дальше» от Кирилла.
- DoD задачи = перечисленные в её строке T-классы (`docs/22` §1) зелёные в CI + краткий отчёт.
- Распределённый T-класс (`PLS-067`): DoD задачи включает только закреплённую за ней часть; чужие части не являются дефектом её реализации. Полный `PASS` такого класса объявляется отдельной записью `docs/26`, а не отчётом задачи. Пока закрыты не все части — статус `PARTIAL` с явным перечнем, никогда не «PASS».
- Тесты пишутся вместе с кодом задачи, не после фазы. Инварианты `docs/14` §5 закрываются правилами БД и тестом T04 «злонамеренный worker» (попытки обхода под ролью `pls_worker` должны отклоняться самой БД).
- Гейты фаз `docs/22` §4 не сжимаются: реальные модели не подключаются к гейтам до зелёных T01–T09, T11, T20 на mock. T05 здесь означает полный PASS всех четырёх частей, поэтому TB-16, TB-19 и TB-29 обязаны быть завершены до этого гейта, несмотря на их размещение в более поздних тематических фазах `docs/25`.
- Коммиты: императив, с TB-ID (`TB-05: transactional transition protocol`). Одна задача — одна ветка/PR либо серия атомарных коммитов.

## Стек и структура

Python 3.12+, FastAPI, aiogram, PostgreSQL (единственный store и очередь: jobs + transactional outbox), pytest + hypothesis для property-тестов, Docker/OCI один image для процессов `web`/`worker`/`scheduler`, Sentry позже (TB-30). Модульный монолит: границы модулей — по компонентам arch §3.1.
