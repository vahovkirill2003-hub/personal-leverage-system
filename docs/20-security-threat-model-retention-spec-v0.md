## 0. Активы (в порядке ценности)

A1 полномочия и их артефакты (Intents, Consents, Grants, Gate Records); A2 канонические записи и история; A3 секреты (bot token, webhook secret, provider keys, DB/storage credentials); A4 персональные данные Кирилла в досье/evidence; A5 evidence-объекты; A6 доступность decision-потока. Приоритет защиты: целостность A1–A2 выше доступности A6 (fail closed).

## 1. Модель угроз по границам

| Актор/вектор | Цель атаки | Механизмы защиты | Остаточный риск |
|---|---|---|---|
| Внешний, знающий webhook URL | Ложные updates, флуд | Secret token до парсинга; inbox-дедупликация; rate-нечувствительность домена (обработка через jobs) | Транспортный DoS до платформенных лимитов; не затрагивает A1–A2 |
| Чужой Telegram-аккаунт / группа / forwarded | Создать решение или consent | Allowlist `from.id`+private chat; forwarded — только материал; opaque Intent без полномочий в payload | Нулевой доменный эффект; security event |
| **Компрометация устройства/аккаунта Telegram Кирилла** | Нажимать кнопки от его имени | В v1 система не выполняет внешних действий и платежей сама; каждый расход — отдельный exact Intent с показанными суммой/предметом; admin-процедура массового supersede Intents (`19` §1.4) + ротация токена | Реальный: злоумышленник с устройством может принимать UA/расходы, которые Кирилл затем исполнял бы вручную — но исполнение остаётся ручным, автоматического ущерба нет. Раскрыт и принят для пилота |
| Prompt injection через документы/страницы | Заставить модель «выполнить команду» | `UNTRUSTED_CONTENT`-канал; tools только через Gateway c allowlist; результат — данные под валидацией `18` §6; никаких hosted tools | Искажение содержания анализа (не полномочий); ловится TR/SA и provenance-дисциплиной |
| Провайдер модели (утечка/retention/обучение) | Доступ к персональному контексту | Минимизация пакетов (§12.2), redaction, dated policy registry + fail-closed preflight, `store:false`, запрет server-side threads/files | Остаточная provider-side retention (abuse monitoring) — учтена в registry; объём минимизирован |
| Компрометация зависимостей / supply chain | Вредоносный код в worker | Раздел 2: pinned lockfiles, immutable image digest, CI-review зависимостей, минимальный набор библиотек | Не нулевой; ограничивается вторым эшелоном БД (раздел 2) |
| Компрометация хоста/платформы | Полный доступ к процессам и БД | TLS, secret store, разделение сред, шифрование at rest, зашифрованные внешние backups | Платформенный компромисс = компромисс инстанса; восстановление из независимых копий; принято для single-node пилота |
| Кража backups | A2, A4 офлайн | Шифрование, отдельный retention, ограниченный доступ, ключи вне backup-хранилища (раздел 4) | Управление ключом — единая точка (см. STV-1) |

## 2. Закрытие `AAR-R1`: привилегии и внутрипроцессное доверие

**Полная модель.** Матрица DB-ролей — `14` §12 (нормативна). Дополнительно фиксируется:

1. **Второй эшелон — правила БД.** Даже при полном компрометировании кода worker невозможно через `pls_worker`: изменить/удалить строку любой append-only таблицы; вставить второй `gate_record` на attempt; изменить `experiment_anchor`; создать второй активный slot; изменить immutable-колонки (`purpose`, request-поля expense, scope grant). Эти запреты — database rules/permissions, не код приложения, и проверяются отдельным тестовым классом «злонамеренный worker».
2. **Монитор инвариантов.** Recovery/integrity job (`14` §10.2) исполняется под отдельной read-only ролью и сверяет projections↔ledger↔hashes по расписанию; расхождение → diagnostic hold + уведомление. Компрометация worker не может отключить монитор (иной процесс, иная роль).
3. **Границы blast radius.** Web не имеет прав на полномочия и гейты; scheduler — только timers/jobs; model-вызовы не получают credentials вообще (данные наружу — только Context Package после DLP). Худший случай компрометации web — потеря транспорта; scheduler — манипуляция временем срабатываний, но не `due_at` и не deadlines (immutable + синхронные guards).
4. **Supply chain.** Pinned lockfiles c hash-верификацией; сборка в CI в один immutable image digest, одинаковый для трёх процессов; новые зависимости — только через явный review; запуск исключительно опубликованного digest.
5. **Секреты.** Только secret store/env защищённого типа; ротация по `19` §1.4 и провайдерным процедурам; секреты никогда не попадают в prompt, логи, traces (redaction-фильтр на выходе логгера), dossier и backups приложения.
6. **Явное допущение.** Внутри одного процесса модульные границы — кодовая дисциплина; полная защита от собственного скомпрометированного кода недостижима в монолите и не заявляется. Заявляется: целостность A1–A2 деградирует максимум до «вставки новых правдоподобных строк», которая обнаруживается монитором и причинностью ledger, и не может тихо переписать историю.

`AAR-R1` этим разделом и `14` §12 закрыт полностью.

## 3. Классификация данных и retention

| Класс | Примеры | Retention | Основание |
|---|---|---|---|
| D1 полномочия/история | A1–A2 | Срок жизни системы; удаление только процедурой раздела 5 при закрытии проекта | Проверяемость цикла |
| D2 персональное содержание досье | Факты о Кирилле, цели, оценки | По `evidence_retention_policy` кейса (`PLS-054`); по умолчанию минимальная проверяемая запись | Минимизация |
| D3 evidence-объекты | Файлы, snapshots | По policy кейса; чувствительный оригинал без необходимости не хранится | `PLS-054` |
| D4 транспорт/диагностика | Логи, traces, inbox payloads | Короткий фикс. срок (настройка пилота), персональный текст редактируется/хэшируется | §13.1 |
| D5 provider-side | Копии у провайдеров моделей | Управляется выбором adapter по registry; собственный retention провайдера не продлевается нашими настройками | §12.6 |
| D6 backups | Всё выше в копиях | Отдельный retention; шифрование; доступ ограничен | §12.5 |

## 4. Backups: защита

Шифрование всех внешних копий (DB dumps, object copies) ключом, который: хранится в secret store отдельно от backup-хранилища; имеет задокументированную процедуру восстановления доступа при утрате основного доступа (минимум — офлайн-копия ключа у Кирилла); ротация ключа не делает старые копии нечитаемыми до истечения их retention (версионирование ключей). Restore-тест ежемесячно подтверждает читаемость именно зашифрованной копии.

## 5. Процедура удаления

Только авторизованная команда retention-роли (`14` §12): криптостирание/удаление объекта → tombstone (id, основание, время, hash) → запись в ledger. Массовое удаление по закрытию проекта — отдельная задокументированная процедура с явным решением Кирилла и сохранением минимального юридически/личностно значимого следа по его выбору.

## 6. Минимизация персональных данных

DLP/redaction перед каждым Model Gateway вызовом (политики `allowed/redact/requires_user_consent/provider_forbidden`); субагенты — псевдонимные идентификаторы; redaction report в manifest пакета; периодический minimization-eval (`18` §7) как регрессионный контроль утечки полей.

## 7. Обнаружение и реагирование (spec-уровень)

Сигналы: security events границ, invariant-monitor, provider-session-reuse violations, storage integrity failures, всплеск denials Tool Gateway. Реакция spec-уровня: hold затронутого кейса, массовый supersede Intents, ротация секретов, восстановление из копий; пошаговые процедуры — Runbook (документ 6), которому передаётся обязательство их детализировать вместе с runbook-частью `AAR-R2`.

## 8. Traceability
