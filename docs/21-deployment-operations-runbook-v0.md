## 1. Среды и релизы

По §15.1–15.2 архитектуры. Эксплуатационные уточнения: production-деплой только тегированного immutable image digest, прошедшего CI и test-среду; перед деплоем — проверка pending миграций (expand-фаза отдельным шагом); после деплоя — readiness всех трёх процессов и контрольный health-трейс (тестовое informational-сообщение в test-чат, никогда в production-чат). Rollback: предыдущий digest; миграции не откатываются — фиксируется forward-fix задача.

## 2. Backup: регламент

| Что | Частота | Проверка |
|---|---|---|
| Provider snapshot/PITR | Непрерывно/по расписанию провайдера | Еженедельная проверка «свежести» WAL/PITR-окна |
| Независимый зашифрованный logical dump | Ежесуточно | Хэш и размер в `object_export_manifest`; читаемость — в ежемесячном drill |

| Ключи шифрования | При ротации | Офлайн-копия у Кирилла актуальна (`20` §4) |

## 3. Restore: процедура (production)

Строгий порядок; исполняется целиком, частичное выполнение запрещено:

1. **Стоп:** остановить worker и scheduler; web перевести в maintenance (retryable 5xx) — вход копится на стороне Telegram.
2. **Восстановление:** выбрать restore-точку (PITR timestamp либо dump); восстановить в отдельный instance/sibling; НЕ переключать приложение.
3. **Integrity:** прогнать recovery/integrity job (`14` §10.2) на восстановленной БД; расхождения зафиксировать.
4. **Object-сверка:** integrity scan evidence-объектов против восстановленных метаданных; недостающие — восстановить из копий или зафиксировать как Defect.
5. **Post-restore реконсиляция (обязательно, `14` §10.3):** supersede всех `pending` Intents; подготовка перевыпуска; outbox-анализ по logical ids; сборка `restore_divergence_report`.
6. **Переключение:** приложение на восстановленную БД; запуск scheduler (overdue-scan по сохранённым `due_at`), затем worker.
7. **Подтверждение:** предъявить Кириллу divergence report; до события `RESTORE_RESUME_CONFIRMED` decision-сообщения не выпускаются; informational о факте восстановления — выпускается.
8. **Закрытие:** записать `restore_test_record`/incident-запись: точка, длительность, находки, решения.

**Ежемесячный drill** — та же процедура на test-среде с синтетическими данными; критерии PASS: шаги 2–5 завершены, integrity без расхождений либо все расхождения объяснены, время в пределах целевого RTO (настройка §9), divergence report собран. Результат — в `restore_test_record`; два подряд FAIL — блокер production-эксплуатации до устранения.

## 4. Diagnostic hold: runbook (закрытие `AAR-R2`, часть 2 из 2)

Спецификация lifecycle — `17` §5; здесь — действия оператора:

1. **При автоматическом входе** (алёрт «case in diagnostic hold»): открыть diagnostic view (§13.4 архитектуры); прочитать `reason_event_id` и расхождение; НЕ править строки БД.
2. **Диагностика:** сверить projection↔transitions↔revisions↔hashes по подсказкам integrity job; определить последнюю согласованную точку.
3. **Устранение:** только compensating-командами реестра `17` (перевычисление projection из ledger; повторная загрузка потерянного объекта; регистрация Defect). Если данные невосстановимы командами — restore-процедура раздела 3 для затронутого контура.
4. **Выход:** `ExitDiagnosticHold` с описанием исправления; проверить, что накопленные `held`-таймеры обработались в порядке `due_at`; убедиться в уведомлении Кирилла о входе и выходе.
5. **Пост-фактум:** incident-запись: причина расхождения, класс (bug/операция/storage), созданные Defects, превентивная задача.

Инвариант-проверка после каждого выхода: day-14/absolute deadline не изменились; preparation ledger без начислений за период hold; никаких новых gate/consent-строк за период hold.

## 5. Инциденты: процедуры (детализация `20` §7)

| Сигнал | Немедленно | Затем |
|---|---|---|
| Security event: серия чужих callback/updates | Ничего доменного не произошло (no-op гарантирован) — оценить объём | При целевой атаке: ротация webhook secret (`19` §1.4) |
| Подозрение компрометации устройства Telegram Кирилла | Массовый supersede всех pending Intents; пауза выпуска decision-сообщений | Ротация bot token; ревизия consents за подозрительное окно с Кириллом; при необходимости hold затронутых кейсов |
| Invariant-monitor: расхождение | Автоматический hold — раздел 4 | Root cause, incident-запись |
| Provider-session reuse / policy block всплеск | Ничего не утекло (fail closed) — проверить конфигурацию adapter | Обновить policy registry либо отключить adapter |
| Storage integrity failure | Evidence помечен недоступным; зависимые gate/closure заблокированы штатно | Восстановление объекта из копии; Defect |
| Утечка секрета (любого) | Ротация этого секрета по его процедуре | Проверка audit-трейла использования; incident-запись |
| Достигнут внутренний spend-стоп | Штатная деградация §13.3 — проверить, что core/read-only живы | Решение Кирилла о бюджете; никакого автоматического продолжения |

## 6. Алёрты: уровни и маршрутизация

Один оператор — значит честные приоритеты, опирающиеся на то, что безопасность обеспечена синхронными guards, а не скоростью реакции:

- **P1 (разбудить):** invariant-monitor расхождение; storage integrity failure по evidence незакрытого кейса; провал восстановления. Канал: пуш/звонок.
- **P2 (в течение дня):** scheduler lag/heartbeat, outbox age, backup freshness, spend soft threshold, всплеск security events. Канал: отдельный служебный Telegram-канал (не production-чат) либо email.
- **P3 (еженедельный обзор):** метрики §13.1, cost против envelope, denials, coverage-статистика.
Пропуск P1 не создаёт риска несанкционированного действия (guards синхронны) — риск ограничен доступностью A6; это раскрыто и принято.

## 7. Ротация секретов: календарь

Bot token и webhook secret — по процедуре `19` §1.4: планово раз в 6 месяцев и немедленно при подозрении. Provider keys, DB/storage credentials — планово раз в 6 месяцев, по процедурам провайдеров, с проверкой readiness после. Backup-ключ — по `20` §4 с версионированием. Каждая ротация — запись без значения секрета.

## 8. Cost-контроль: эксплуатация

Еженедельно: фактическое потребление против envelope по категориям §13.2; при soft threshold — анализ драйверов до продолжения. **Чек-лист активации production (перед первым платным ресурсом, §13.3):** датированный envelope со всеми полями таблицы §13.3 → проверки §20.2 архитектуры (оплата/доступность/data policy; restore rehearsal; storage conformance) → явное решение Кирилла с датой, scope и ceiling → только затем активация. Чек-лист неприменим частично: незакрытый пункт блокирует активацию.
