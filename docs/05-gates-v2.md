# Personal Leverage System
## Gates Contract v2: Technical Review, System Acceptance и User Acceptance

**Статус:** кандидат на пользовательскую приёмку после независимого аудита  
**Дата:** 1 августа 2026  
**Основание:** принятые документы v1, решения `PLS-001–PLS-062`, независимый аудит `06-independent-system-audit-v1.md` и решения заказчика по обязательным исправлениям  
**Область:** продуктовая семантика трёх гейтов одного Decision-to-Action Workflow  
**За рамками:** агенты, модели, промпты, программная архитектура, API, базы данных, JSON Schema, Telegram-бот и код

## 1. Назначение документа

Этот документ определяет продуктовый контракт трёх последовательных гейтов:

1. **Technical Review** — независимая проверка технической допустимости и доказательной конструкции.
2. **System Acceptance** — проверка соответствия полной редакции досье продуктовому контракту PLS.
3. **User Acceptance** — осознанное решение Кирилла о ценностной приемлемости и разрешении на запуск или возобновление.

Гейт — это **ответственность, проверка и зафиксированное решение о переходе**, а не обязательно отдельный агент, модель, вызов, сообщение или технический компонент. Несколько продуктовых ролей могут быть реализованы разными способами, но их полномочия, критерии и записи нельзя смешивать.

Гейты не гарантируют желаемого внешнего результата. Они гарантируют, что до исполнения:

- проверяемая логика эксперимента технически допустима;
- полная редакция соответствует продуктовому контракту;
- Кирилл понимает предмет решения, риски, неопределённость и разрешаемые действия;
- исполнение может начаться только в явно принятых границах.

## 2. Общие понятия

### 2.1. Редакция досье

**Редакция** — точное целостное состояние кандидатной или принятой версии досье в момент гейта. Любая правка между гейтами создаёт новую редакцию, даже если она редакционная и предполагается нематериальной.

Каждый результат гейта относится только к указанной в Gate Record редакции. Результат по редакции `R1` не действует для `R2`, пока владелец соответствующего гейта не:

- проведёт гейт заново для `R2`; либо
- явно оформит допустимый `carry-forward` с `R1` на `R2`.

Молчаливый перенос результата, вывод о применимости «по смыслу» без записи и показ пользователю иной редакции запрещены.

### 2.2. Полная приёмочная цепочка

Для `INITIAL` и `REVALIDATED` исполняемая редакция должна иметь применимые результаты в порядке:

`Technical Review → System Acceptance → User Acceptance`.

Порядок означает зависимость полномочий, а не обязательное число технических вызовов. Более поздний гейт может вернуть работу, но не может задним числом изменить, удалить или приписать иной смысл результату раннего гейта.

### 2.3. Прохождение гейта

Гейт считается пройденным только когда одновременно:

1. определена точная редакция;
2. получен полный обязательный вход;
3. применены заранее зафиксированные критерии;
4. выполнены условия прохождения конкретного гейта;
5. создан полный Gate Record;
6. указан один разрешённый следующий переход;
7. результат выражен допустимым результатом этого гейта.

Обсуждение, промежуточный комментарий, молчание, частичное согласие или отсутствие новых замечаний не являются прохождением.

До предъявления пакета на первый User Acceptance вся активная работа Technical Review и System Acceptance, их возвраты, исправления и обязательные Gate Records входят в единый 60-минутный бюджет подготовки. Параллельная работа не создаёт отдельный бюджет. Gate Record нельзя вынести за границу лимита: без него гейт не пройден. Фактическое активное время каждого гейта фиксируется отдельно для калибровки; жёстких подлимитов до завершения двух пилотных циклов нет.

### 2.4. Источник дефекта и источник возврата

- **Источник дефекта** — требование или логическая область, где наблюдается несоответствие.
- **Источник возврата** — ближайшая стадия workflow или ответственная продуктовая область, способная устранить дефект без ненужного возврата всего кейса в Intake.

Возврат обязан указывать оба понятия и не может быть безадресным требованием «доработать досье».

## 3. Единая классификация замечаний

Классификация применяется Technical Review и используется System Acceptance при проверке закрытия дефектов и допустимости пробелов.

Четырёхклассная классификация этого раздела выведена из `PLS-026`, `PLS-027`, `PLS-029`, `PLS-039` и `PLS-061`; она не является отдельным новым решением журнала.

| Класс | Определение | Последствие | Можно ли продолжать к следующему гейту | Можно ли принять Кириллу как есть |
|---|---|---|---|---|
| **Критический дефект** | Нарушение, при котором исполнение недопустимо: отсутствует или разрушена ключевая доказательная связь; не определены безопасность, полномочия, данные, существенный расход или критический риск; действие незаконно, неэтично, необратимо без принятия либо неинтерпретируемо; результат гейта недостоверен | Немедленный блок затронутых действий; `TECH_REVIEW_RETURNED`, а после исчерпания обычных возвратов — эскалация; Closure, если безопасное исправление нецелесообразно | Нет | Нет |
| **Обязательный дефект** | Требование обязательно для технической допустимости или продуктового контракта, но дефект не создаёт немедленной недопустимости, пока Execution заблокирован | Исправление, сужение scope, новые данные или дополнительный ресурс; обычный возврат в пределах лимита | Нет | Нет |
| **Раскрываемый некритичный пробел** | Неполнота или остаточная неопределённость, которая не относится к запрещённой категории, не разрушает безопасность, полномочия, доказательную связь или интерпретацию и может быть явно показана Кириллу | Technical Review может пройти; System Acceptance решает допустимость; каждый пробел отдельно принимается Кириллом | Да, только через `ACCEPTED_WITH_DISCLOSED_GAPS` | Да, только явно и поштучно на User Acceptance |
| **Рекомендация** | Улучшение, не обязательное для допустимости, соответствия контракту или осознанного решения | Записывается без блокировки; может быть принято, отложено или отклонено | Да | Отдельная приёмка не требуется, если рекомендация не меняет принимаемый контракт |

### 3.1. Правила классификации

1. Класс определяется по влиянию дефекта, а не по трудоёмкости исправления.
2. Неизвестность в запрещённой категории не может быть понижена до раскрываемого пробела.
3. Несколько одинаковых симптомов одного корневого дефекта могут быть объединены в одно замечание, но затронутые места перечисляются полностью.
4. Разные корневые дефекты не объединяются для искусственного уменьшения числа замечаний.
5. Рекомендация не может содержать скрытое обязательное условие прохождения.
6. При сомнении между двумя классами до получения достаточного основания применяется более строгий класс.
7. Только Technical Reviewer вправе обоснованно переклассифицировать собственное замечание Technical Review.

## 4. Общий контракт замечания Technical Review

Каждое замечание Technical Review содержит:

| Поле | Обязательная семантика |
|---|---|
| Идентификатор | Уникальная стабильная ссылка на замечание; не меняется между итерациями |
| Точная редакция | Редакция, на которой дефект наблюдался |
| Нарушенное требование | Конкретный критерий Technical Review, принятый документ или инвариант |
| Наблюдаемый дефект | Проверяемое описание того, что отсутствует, противоречит или не работает; без подмены предположением о причине |
| Влияние | Как дефект влияет на решение, безопасность, полномочия, исполнение, доказательство или интерпретацию |
| Критичность | Один из четырёх классов раздела 3 |
| Критерий исправления | Наблюдаемый результат, после которого замечание может быть закрыто |
| Затронутая часть досье | Канонические записи и логические области, а не копии представлений |
| Источник возврата | Ближайшая стадия или продуктовая область, где дефект должен быть устранён |
| Номер итерации | Номер попытки Technical Review и номер обычного возврата, если он создан |

Дополнительно при повторной проверке фиксируются: что изменилось, какое доказательство исправления рассмотрено, закрыто ли замечание, создан ли новый дефект и является ли он следствием прежнего исправления.

## 5. Technical Review

### 5.1. Назначение

Technical Review независимо отвечает на вопрос:

> Является ли предлагаемая проверка технически допустимым, выполнимым, безопасным и интерпретируемым способом получить доказательство, способное повлиять на заявленное решение?

Гейт проверяет не привлекательность жизненного выбора и не полноту оформления досье как продукта, а качество фактов, гипотезы, действий, доказательств, ограничений и правил вывода.

### 5.2. Владелец

Владелец — **Technical Reviewer**.

Technical Reviewer:

- несёт ответственность за независимую техническую оценку;
- классифицирует и закрывает собственные замечания;
- единолично определяет техническую допустимость;
- может выдать `carry-forward` только для результата Technical Review;
- не может делегировать Кириллу принятие обязательного или критического дефекта.

Автор проверяемой логики не может принять собственную работу вместо независимого Technical Review. Независимость означает отдельную проверку против критериев и возможность вынести блокирующее замечание независимо от предпочтительного результата.

### 5.3. Границы ответственности

Technical Reviewer отвечает за техническую допустимость и качество доказательной конструкции.

Он не отвечает за:

- ценностный выбор Кирилла;
- решение, стоит ли Кириллу запускать допустимый эксперимент;
- соответствие всех 27 логических областей продуктовому контракту как целому;
- пользовательскую понятность Telegram-summary как финальное решение System Acceptance;
- выдачу новых полномочий, подтверждение расхода или внешнего действия;
- изменение scope, цели или риска ради получения проходного результата;
- окончательное принятие раскрываемого пробела Кириллом.

### 5.4. Точный вход

Обязательный вход Technical Review:

1. идентификатор кейса;
2. точная кандидатная редакция полного досье;
3. выбранная глубина: минимальная, стандартная или повышенная, с основаниями;
4. канонические записи Decision Core, Execution Record и Audit Appendix, обязательные к этой стадии;
5. реестр значимых фактов, источников, дат и статусов проверки;
6. контракт эксперимента;
7. контракты всех предполагаемых внешних действий и готовый Execution Pack;
8. success, review и stop conditions;
9. правила интерпретации результата и ожидаемая сила доказательства;
10. лимиты срока, нагрузки, подготовки и денег;
11. данные, полномочия, подтверждения, риски, обратимость и хранение доказательств;
12. раскрытые предполагаемые пробелы;
13. заранее зафиксированные критерии этого Technical Review и качества ожидаемого результата;
14. для повторной попытки — все прежние замечания, их статус, номера итераций и delta редакции;
15. для переноса — исходный Gate Record и полный delta между исходной и целевой редакциями.

Отсутствие обязательного входа является обязательным или критическим дефектом, а не основанием достроить содержание молча внутри гейта.

### 5.5. Что Technical Review обязан проверить

Technical Reviewer независимо проверяет:

1. **Решающее неизвестное.** Оно действительно способно изменить решение и не подменено общей темой.
2. **Полную связь.** Прослеживается цепочка `решающее неизвестное → внешнее действие → ожидаемое доказательство → правило интерпретации → следующее решение`.
3. **Качество фактов.** Значимые факты отделены от утверждений, предположений и рекомендаций; происхождение и статус проверки ясны.
4. **Актуальность фактов.** Критические внешние факты имеют достаточную дату проверки и остаются применимыми к сроку эксперимента.
5. **Альтернативные объяснения.** Перечислены правдоподобные причины наблюдаемого результата, способные изменить вывод.
6. **Проверяемость гипотезы.** Возможен наблюдаемый результат, который поддержит, ослабит или оставит гипотезу inconclusive; гипотеза не сформулирована так, чтобы любой исход её подтверждал.
7. **Наблюдаемость условий.** Success, review и stop conditions имеют наблюдаемое событие, порог или доказательство, момент проверки и однозначное последствие.
8. **Выполнимость.** Действия доступны Кириллу в заявленном порядке, зависят от обозначенных внешних сторон и не требуют скрытого ресурса.
9. **Срок.** Эксперимент укладывается в 3–14 дней; контрольные сроки и остаток времени реалистичны; ожидание не создаёт скрытого продления.
10. **Лимиты.** Подготовка, нагрузка, количество действий и дополнительные ресурсы измеримы и имеют реакцию на достижение.
11. **Расходы.** Каждый возможный расход отделён, имеет сумму или допустимую верхнюю границу для показа, назначение и индивидуальное подтверждение; пакет не создаёт денежного полномочия.
12. **Данные.** Передаваемые и хранимые данные минимальны, конкретны, имеют цель, получателя, форму и срок либо событие хранения.
13. **Полномочия.** Каждое внешнее действие либо отдельно подтверждается, либо полностью входит в допустимый бесплатный пакет; полномочия не выводятся из общего согласия.
14. **Безопасность.** Учтены вред Кириллу и третьим лицам, текущая работа, конфиденциальность, юридические и репутационные последствия, а также безопасная остановка обязательств.
15. **Обратимость.** Указаны отменимость действия, последствия ошибки, необратимые обязательства и способ минимизировать ущерб.
16. **Доказательная сила.** Ожидаемое свидетельство способно ответить на решающее неизвестное; сила обозначена как сильная, умеренная, слабая или недостаточная с основанием.
17. **Подтверждение действия.** Определён независимый след либо допустимая пользовательская аттестация с обязательными полями и ограничением силы.
18. **Правила интерпретации.** До запуска определено, какие результаты поддерживают, ослабляют или не разрешают гипотезу; запрещены ретроспективное изменение критерия и выбор удобного объяснения.
19. **Качество ожидаемого результата.** Заранее описано, какой результат считается достаточно полным, точным, проверяемым и связанным с решением.
20. **Разумность ex ante.** Способ проверки выглядит разумным до знания результата; невыполнение плана нельзя позже назвать inconclusive-экспериментом.

### 5.6. Что Technical Reviewer не имеет права решать

Technical Reviewer не вправе:

- принять за Кирилла риск, компромисс, раскрытый пробел, расход или внешнее действие;
- считать технически допустимым критический или обязательный дефект ради скорости;
- менять гипотезу, scope, действие, критерий или интерпретацию внутри Gate Record;
- выдавать `ACCEPTED` или `ACCEPTED_WITH_DISCLOSED_GAPS` от имени System Acceptance;
- делать вывод, что технически допустимый эксперимент ценностно приемлем Кириллу;
- понижать замечание для обхода запрещённой категории;
- оценивать новую редакцию под результатом старой без повторного гейта или `carry-forward`;
- изменять заранее зафиксированные критерии после начала Execution без новой редакции.

### 5.7. Точный выход и допустимые результаты

Точный выход — Gate Record Technical Review для одной редакции, полный список замечаний, статус прежних замечаний и ровно один результат:

| Результат / событие | Семантика | Следующий разрешённый переход |
|---|---|---|
| `TECH_REVIEW_PASSED` | Для точной редакции нет открытых критических или обязательных дефектов; раскрываемые пробелы и рекомендации перечислены | `SYSTEM_ACCEPTANCE` той же редакции либо новой редакции только после допустимого `carry-forward`/повторного review |
| `TECH_REVIEW_RETURNED` | Есть хотя бы один критический или обязательный дефект и доступен первый или второй обычный возврат | `REWORK_REQUIRED` к ближайшему источнику дефекта |
| `THIRD_MANDATORY_DEFECT` | После двух обычных возвратов очередная попытка всё ещё содержит или вновь обнаруживает блокирующий обязательный либо критический дефект | `TECHNICAL_REVIEW_ESCALATION` |

Техническое имя `THIRD_MANDATORY_DEFECT` применяется как событие достижения лимита блокирующих дефектов; фактический класс каждого замечания сохраняется и не понижается.

### 5.8. Обязательная запись в досье

В Audit Appendix сохраняются:

- полный Gate Record;
- точная редакция;
- применённые критерии;
- все замечания по контракту раздела 4;
- закрытие или переклассификация каждого прежнего замечания;
- номер попытки и число обычных возвратов;
- результат и разрешённый переход;
- любой `carry-forward`;
- дата и владелец.

Decision Core показывает применимость результата, наличие раскрываемых пробелов и блокирующий итог, но не дублирует полный реестр замечаний.

### 5.9. Условия прохождения

`TECH_REVIEW_PASSED` допустим только если:

1. весь обязательный вход проверен;
2. все двадцать групп критериев раздела 5.5 применены;
3. нет открытого критического или обязательного дефекта;
4. каждый раскрываемый пробел относится к допустимой категории и имеет влияние;
5. рекомендации не маскируют обязательные требования;
6. все прежние дефекты закрыты либо обоснованно переклассифицированы самим Technical Reviewer;
7. результат относится к точной редакции;
8. Gate Record полон.

### 5.10. Условия возврата

`TECH_REVIEW_RETURNED` обязателен, если до исчерпания двух обычных возвратов:

- обнаружен хотя бы один критический или обязательный дефект;
- отсутствует обязательный вход;
- исправление прежнего дефекта не доказано;
- delta скрыт, неполон или не позволяет установить редакцию;
- критерии изменены без новой редакции;
- независимость проверки нарушена.

Возврат направляется к ближайшему источнику, содержит критерии исправления и обязан перечислить все блокирующие дефекты, которые разумно можно выявить по полному представленному входу, чтобы не создавать последовательный «капельный» review.

### 5.11. Условия эскалации

Переход в `TECHNICAL_REVIEW_ESCALATION` обязателен, когда после двух обычных возвратов очередная попытка содержит любой блокирующий дефект. Допустимые пути:

1. исправление;
2. сужение scope;
3. получение новых данных;
4. предоставление дополнительного конкретного ресурса;
5. Experiment Closure;
6. обоснованная переклассификация самим Technical Reviewer, если категория допускает раскрываемый пробел.

Кирилл выбирает допустимый путь, ресурс или прекращение, но не отменяет технический дефект. Возврат к Technical Review происходит только после выбранного разрешения и новой редакции либо доказательства исправления.

## 6. Лимит возвратов Technical Review

### 6.1. Единица счёта

Один **обычный возврат** — один Gate Record с результатом `TECH_REVIEW_RETURNED`, независимо от числа замечаний в нём. В рамках одной попытки Reviewer обязан раскрыть все обнаруженные блокирующие замечания, которые разумно можно выявить по полному представленному входу.

Счётчик ведётся за всю жизнь одного кейса. Новая редакция, материальное изменение, User Acceptance, начало Execution и Cycle Review его не сбрасывают. Только новый связанный кейс получает новый счётчик.

### 6.2. Порядок

1. Первая попытка: pass либо обычный возврат № 1.
2. Вторая попытка после исправления: pass либо обычный возврат № 2.
3. Любая следующая попытка в том же кейсе: pass, если блокирующих дефектов нет; иначе любой открытый критический или обязательный дефект вызывает `THIRD_MANDATORY_DEFECT` и `TECHNICAL_REVIEW_ESCALATION`.

Новый блокирующий дефект на третьей попытке также вызывает эскалацию, если его нельзя было проверить раньше из-за неполного входа или он возник вследствие исправления. Если Reviewer без основания не раскрыл ранее наблюдаемый дефект, это регистрируется как дефект самого процесса review и не используется для искусственного продления обычных возвратов.

### 6.3. Переклассификация

Переклассификация допустима только если Reviewer запишет:

- исходный класс и новый класс;
- новые данные или исправленное понимание;
- почему влияние больше не блокирует техническую допустимость;
- почему пробел не относится ни к одной запрещённой категории;
- остаточный риск и способ раскрытия;
- редакцию и дату.

Переклассификация не является исправлением, если фактический дефект сохранился. Она не может обходить scope, решающее неизвестное, доказательную связь, условия, лимиты, расходы, действия, данные, полномочия, безопасность, критические основания или правила интерпретации.

## 7. System Acceptance

### 7.1. Назначение

System Acceptance отвечает на вопрос:

> Соответствует ли полная точная редакция досье принятому продуктовому контракту PLS и готова ли она быть предъявлена Кириллу как однозначный объект решения?

System Acceptance не повторяет Technical Review и не выбирает заново качество гипотезы. Оно проверяет полноту, согласованность, происхождение гейтов, закрытие дефектов, допустимость пробелов и готовность пользовательского и исполнительного контуров.

### 7.2. Владелец

Владелец — **System Acceptor**.

System Acceptor:

- определяет соответствие продуктовым контрактам и инвариантам;
- классифицирует досье как полностью принятое, принятое с допустимыми пробелами или возвращённое;
- может выдать `carry-forward` только для System Acceptance;
- не может переопределить технический результат или принять решение за Кирилла.

### 7.3. Границы ответственности

System Acceptor отвечает за соответствие полной версии продукта, а не за повторную техническую экспертизу.

Он не вправе:

- задним числом менять `TECH_REVIEW_PASSED` или замечания Reviewer;
- самостоятельно закрывать технический дефект;
- принять критический или обязательный дефект как раскрываемый пробел;
- определить ценностную приемлемость, остаточный риск или готовность Кирилла действовать;
- выдать полномочие на действие, передачу данных или расход;
- исправить досье внутри Gate Record и принять уже изменённое содержание под старой редакцией;
- объявить Telegram-summary источником истины при расхождении с полной версией.

Если System Acceptor обнаруживает вероятный технический дефект, он возвращает работу с указанием несоответствия и источника, не переписывая прежний Technical Review. Исправленная редакция проходит применимые гейты заново.

### 7.4. Точный вход

Обязательный вход System Acceptance:

1. идентификатор кейса;
2. точная полная редакция досье;
3. применимый Gate Record `TECH_REVIEW_PASSED` для этой редакции либо явный Technical Review carry-forward;
4. все замечания Technical Review и доказательства их закрытия/переклассификации;
5. все 27 логических областей в объёме, обязательном к этой стадии;
6. выбранная глубина и проверка триггеров повышенной глубины;
7. контракт эксперимента, conditions, контракты действий и Execution Pack;
8. лимиты, срок, расходы, данные, полномочия, риски, безопасность и правила хранения;
9. список предлагаемых раскрываемых пробелов;
10. Telegram-summary для предстоящей User Acceptance либо материал, из которого проверяется его точное соответствие;
11. заранее зафиксированные критерии System Acceptance и пользовательского решения;
12. история редакций, delta и применимые carry-forward.

### 7.5. Что System Acceptance обязан проверить

System Acceptor проверяет:

1. присутствие всех обязательных логических областей либо обоснованное `не применимо`;
2. достаточность выбранной глубины и обязательность повышенной глубины;
3. один источник истины каждой записи и отсутствие конфликтующих копий;
4. согласованность идентификатора кейса и точной редакции во всех входах;
5. применимость Technical Review к этой редакции;
6. закрытие всех критических и обязательных дефектов;
7. полноту записей раскрываемых пробелов и рекомендаций;
8. соблюдение лимита Technical Review и корректность эскалации;
9. срок 3–14 дней, предел 14 дней и контрольные сроки ожидания;
10. лимиты подготовки, нагрузки, количества действий и ресурсов;
11. индивидуальную выделенность каждого возможного расхода;
12. границы бесплатного пакета и отсутствие денежного полномочия в пакете;
13. конкретность внешних действий, их адресатов, содержания, данных, рисков и доказательств;
14. действительность и ограниченность полномочий;
15. минимизацию, передачу и хранение данных;
16. полноту существенных рисков, безопасности, обратимости и обязательств;
17. готовность Execution Pack без необходимости придумывать содержание после User Acceptance;
18. понятность каждого решения, которое должен принять Кирилл;
19. различимость фактов, предположений, неизвестных, рекомендаций и пользовательских решений;
20. соответствие Telegram-summary полной канонической версии;
21. допустимость каждого раскрытого пробела;
22. наличие заранее зафиксированных критериев результата, возврата и доказательства выполнения;
23. отсутствие скрытого материального изменения и молчаливого переноса гейта.

### 7.6. Что System Acceptor не имеет права решать

Помимо границ раздела 7.3, System Acceptor не имеет права:

- повторно оценивать техническую силу вместо Reviewer, если не обнаружено контрактное несоответствие;
- считать согласие Кирилла предполагаемым;
- объединять отдельные расходы в общее согласие;
- принимать раскрытые пробелы от имени Кирилла;
- расширять пакет бесплатных действий;
- менять критерии приёмки или качество результата после начала Execution;
- допускать продолжение при расхождении полной версии и Telegram-summary.

### 7.7. Точный выход и допустимые результаты

Точный выход — Gate Record System Acceptance для одной редакции, список раскрытых пробелов и ровно один результат:

| Результат | Семантика | Следующий разрешённый переход |
|---|---|---|
| `ACCEPTED` | Полная редакция соответствует продуктовому контракту; раскрываемых некритичных пробелов нет | `USER_ACCEPTANCE/INITIAL` или `USER_ACCEPTANCE/REVALIDATED` той же редакции |
| `ACCEPTED_WITH_DISCLOSED_GAPS` | Контракт выполнен настолько, чтобы безопасно и осмысленно продолжать; существуют только допустимые, поштучно раскрытые некритичные пробелы | `USER_ACCEPTANCE/INITIAL` или `USER_ACCEPTANCE/REVALIDATED`; каждый пробел требует отдельного решения Кирилла |
| `RETURNED` | Нарушен продуктовый контракт, редакция/гейт несогласованы, дефекты не закрыты, Execution Pack не готов либо есть недопустимый пробел | `REWORK_REQUIRED` к ближайшему источнику; после новой редакции применимые гейты проходят заново |

### 7.8. Обязательная запись в досье

В Audit Appendix сохраняются:

- полный Gate Record;
- точная редакция и применимый Technical Review;
- проверенные продуктовые критерии;
- статус каждого обязательного дефекта;
- каждый раскрытый пробел или причина возврата;
- результат, дата, владелец и следующий переход;
- любой `carry-forward`.

Decision Core показывает результат, все пробелы для решения Кирилла, критические ограничения и готовность Execution Pack.

### 7.9. Условия `ACCEPTED`

`ACCEPTED` допустим, только если:

1. Technical Review применим к той же редакции;
2. все обязательные области и записи полны;
3. критические и обязательные дефекты закрыты;
4. раскрываемых пробелов нет;
5. лимиты, расходы, данные, полномочия, риски и действия однозначны;
6. Execution Pack готов;
7. решения Кирилла сформулированы понятно;
8. полная версия и Telegram-summary согласованы;
9. Gate Record полон.

### 7.10. Условия `ACCEPTED_WITH_DISCLOSED_GAPS`

Результат допустим, только если одновременно:

1. выполнены все условия `ACCEPTED`, кроме полноты в разрешённых некритичных категориях;
2. ни один пробел не относится к запрещённому перечню раздела 8;
3. каждый пробел имеет полную запись;
4. влияние пробелов не делает решение, действие или результат двусмысленным;
5. Кириллу будет предложено отдельное принятие каждого пробела;
6. отказ принять любой пробел не может быть истолкован как принятие остальных или всего досье.

### 7.11. Условия возврата

`RETURNED` обязателен, если:

- нет применимого `TECH_REVIEW_PASSED`;
- редакции или канонические записи расходятся;
- открыт критический или обязательный дефект;
- пробел находится в запрещённой категории;
- обязательная область отсутствует без обоснованного `не применимо`;
- нарушены лимиты, полномочия, расходы, данные или безопасность;
- Execution Pack требует содержательного достраивания после приёмки;
- пользовательское решение непонятно или смешано с системной рекомендацией;
- Telegram-summary расходится с полной версией;
- критерии или delta скрыты.

### 7.12. Условия эскалации

System Acceptance не имеет отдельного числового лимита возвратов. Cycle Review по разделу 23 обязателен, если возврат повторяет корневой дефект, не даёт содержательного прогресса, повторяет позиции без новых данных либо угрожает лимиту подготовки или актуальности. Дополнительная эскалация обязательна, если:

- возвраты образуют цикл без нового содержания;
- System Acceptor и Technical Reviewer расходятся в классификации одного и того же риска;
- устранение несоответствия требует изменения принятого продуктового контракта;
- невозможно определить владельца исправления;
- достижение лимита подготовки требует от Кирилла выбора scope, данных, дополнительного времени или Closure.

Cycle Review и эскалация не являются принятием. До разрешения кейс не переходит в User Acceptance.

## 8. Контракт раскрытого некритичного пробела

### 8.1. Обязательная запись каждого пробела

Каждый пробел имеет:

1. идентификатор;
2. точную редакцию;
3. что именно неизвестно, отсутствует или имеет ограниченную надёжность;
4. каноническую область досье;
5. почему пробел не критический и не обязательный;
6. влияние на уверенность, действие, риск и интерпретацию;
7. остаточный риск продолжения;
8. временную меру или способ закрытия;
9. срок/событие повторной проверки, если применимо;
10. основание допустимости System Acceptor;
11. отдельное решение Кирилла на User Acceptance;
12. статус после приёмки.

### 8.2. Полный перечень категорий, где пробелы недопустимы

`ACCEPTED_WITH_DISCLOSED_GAPS` не допускается при пробеле в:

1. scope и предмете решения;
2. решающем неизвестном;
3. связи `неизвестное → действие → доказательство → интерпретация → решение`;
4. проверяемости гипотезы на уровне, необходимом для различения результата;
5. success, review или stop conditions;
6. правилах интерпретации и критериях качества ожидаемого результата;
7. сроке эксперимента и абсолютном пределе 14 дней;
8. лимитах подготовки, нагрузки, количества действий или ресурсов;
9. расходах, их назначении и индивидуальном подтверждении;
10. составе, содержании, адресате, независимой системе или границах любого внешнего действия;
11. передаваемых данных, минимизации, хранении и праве их использовать;
12. полномочиях и подтверждениях;
13. безопасности Кирилла и третьих лиц;
14. риске для текущей работы, юридическом, репутационном или ином существенном риске;
15. необратимом обязательстве, обратимости и безопасной остановке;
16. критическом основании решения или критическом внешнем факте, включая его источник и актуальность;
17. способе подтверждения выполнения и минимально необходимой доказательной силе;
18. применимости Technical Review, точной редакции или истории обязательных дефектов;
19. обязательном триггере повышенной глубины;
20. расхождении Telegram-summary с полной версией в части решения, риска, действия, данных, полномочия или расхода.

Допустимыми кандидатами на раскрываемый пробел могут быть только не влияющие на перечисленные категории: неполная историческая детализация baseline при честно зафиксированном текущем baseline; второстепенный контекст; необязательная альтернатива; оптимизационная деталь; дополнительное, но не минимально необходимое доказательство.

### 8.3. Правило интерпретации пробела и остаточной неопределённости

**Запрещённый пробел** — отсутствующее, неизвестное или неоднозначное содержание, без которого нельзя установить хотя бы одно из следующего:

- безопасность Кирилла или третьих лиц;
- наличие и границы полномочий;
- исполнимость действия и эксперимента;
- проверяемость действия, доказательства или результата;
- осознанность пользовательского решения.

Известная, описанная и ограниченная **остаточная неопределённость** не становится запрещённым пробелом только потому, что риск невозможно устранить полностью. Для допустимости она обязана иметь:

1. известный источник;
2. описанное влияние на решение, действие, риск и интерпретацию;
3. установленные границы;
4. меры снижения;
5. явное принятие Кириллом.

Если границы или последствия неопределённости нельзя оценить, она классифицируется как обязательный либо критический дефект по фактическому влиянию. Называть её раскрываемым пробелом или остаточным риском для обхода возврата запрещено.

## 9. User Acceptance: общий контракт

### 9.1. Назначение

User Acceptance — не подтверждение качества работы системы. Это осознанное решение Кирилла:

- является ли предмет решения лично значимым и корректно понятым;
- приемлемы ли компромиссы, остаточная неопределённость и остаточный риск;
- какие внешние действия он разрешает;
- какие данные разрешает передать;
- какой бесплатный пакет принимает;
- готов ли он выделить заявленную нагрузку и срок;
- разрешает ли он запуск либо возобновление.

Техническое качество уже определено Technical Review, а соответствие контракту — System Acceptance. Кирилл не заменяет эти гейты и не может принять критический или обязательный дефект.

### 9.2. Владелец

Владелец — **Кирилл**.

Только Кирилл определяет ценностную приемлемость, остаточный риск и разрешение на запуск. Только Кирилл может выдать `carry-forward` результата User Acceptance на доказанно нематериальную редакцию, но такой перенос не создаёт денежного полномочия, не принимает новый пробел и не расширяет внешнее действие.

### 9.3. Границы ответственности

Кирилл отвечает за личное решение и предоставляемые полномочия. Он не отвечает за:

- техническую допустимость;
- соответствие досье продуктовому контракту;
- переклассификацию обязательного или критического дефекта;
- доказательство нематериальности для чужого гейта;
- подтверждение расхода, который не был показан индивидуально;
- будущие действия, отсутствующие в принятой редакции или бесплатном пакете.

### 9.4. Точный вход

Для `INITIAL` и `REVALIDATED` обязательны:

1. идентификатор кейса и точная предъявляемая редакция;
2. применимые `TECH_REVIEW_PASSED` и `ACCEPTED` либо `ACCEPTED_WITH_DISCLOSED_GAPS`;
3. обязательный Telegram-summary, совпадающий с полной версией;
4. Decision Core и доступ к критическим элементам Execution Record и Audit Appendix;
5. список всех решений, требующих явного принятия;
6. каждый раскрытый пробел отдельной записью;
7. каждый внешний шаг и предлагаемый бесплатный пакет;
8. каждый возможный расход как отдельный будущий запрос подтверждения либо отдельное подтверждение, если расход уже ставится на решение;
9. передаваемые и хранимые данные;
10. срок, нагрузка, лимиты, риски, обратимость и границы автономности;
11. критерии User Acceptance, качества результата, возврата и доказательства выполнения;
12. история редакций и применимые carry-forward.

Для `RESUMPTION_ONLY` точный вход определён в разделе 12.

### 9.5. Что Кирилл принимает отдельно в `INITIAL` и `REVALIDATED`

В Gate Record должны быть раздельно и однозначно зафиксированы решения по:

1. предмету решения и scope;
2. baseline и реальным альтернативам, включая бездействие;
3. гипотезе;
4. решающему неизвестному;
5. условиям эксперимента, включая success, review, stop и правила интерпретации;
6. каждому типу внешнего действия и его содержанию;
7. бесплатному пакету действий со всеми границами;
8. нагрузке, сроку, лимитам и контрольным моментам;
9. существенным рискам, обратимости и обязательствам;
10. передаваемым данным, получателям, цели и правилам хранения;
11. каждому раскрытому пробелу поштучно;
12. остаточной неопределённости и ожидаемой силе доказательства;
13. границам автономности системы и действиям, которые останутся заблокированы до отдельного подтверждения.

Эти решения могут быть представлены компактно, но нельзя скрывать отдельный предмет внутри общего «согласен». Частичное принятие не создаёт полный `USER_ACCEPTED`.

### 9.6. Что User Acceptance не означает

Принятие досье:

- не подтверждает качество Technical Review или System Acceptance;
- не разрешает любой будущий внешний шаг;
- не разрешает изменение адресата, смысла, данных, срока, риска или интерпретации;
- не подтверждает ни один будущий расход автоматически;
- не разрешает передачу данных вне явно принятого контракта;
- не превращает рекомендацию системы в решение Кирилла;
- не отменяет review/stop conditions;
- не переносится на новую редакцию молча.

### 9.7. Расходы и бесплатный пакет

Каждый расход подтверждается **индивидуально**: конкретные сумма или показанная верхняя граница, назначение, получатель, момент, риск и невозможность/возможность отмены. Общее принятие досье, бюджета, категории расходов или максимального бюджета не является подтверждением конкретного расхода.

Бесплатные действия могут быть подтверждены одним пакетом только если заранее определены:

- типы и максимальное количество действий;
- адресаты либо узкое правило выбора;
- содержание и неизменяемый смысл сообщения;
- передаваемые данные;
- временные границы;
- существенный риск;
- условия отмены;
- ожидаемый след и доказательство.

Выход за любую границу прекращает применимость пакета к соответствующему действию. Требуется отдельное подтверждение либо, при материальном изменении, новая редакция и три гейта.

### 9.8. Допустимые результаты

| Результат | Допустимые режимы | Семантика | Следующий разрешённый переход |
|---|---|---|---|
| `USER_ACCEPTED` | `INITIAL`, `REVALIDATED` | Все обязательные предметы приняты явно; каждый пробел принят отдельно; запуск разрешён в указанных границах. Первый такой результат, разрешающий первый переход в Execution, однократно создаёт `EXPERIMENT_STARTED` | `EXECUTION` той же редакции при актуальности и действующих полномочиях |
| `USER_RETURNED` | `INITIAL`, `REVALIDATED`, `RESUMPTION_ONLY` | Кирилл явно запрашивает доработку либо материальное изменение; это возврат содержания, а не окончательное решение прекратить кейс | `REWORK_REQUIRED` либо `REVALIDATION_REQUIRED` по материальности и источнику изменения |
| `USER_DEFERRED` | `INITIAL`, `REVALIDATED`, `RESUMPTION_ONLY` | Кирилл явно откладывает решение; согласие не возникло | `PAUSED_USER` по правилам раздела 13 |
| `USER_REJECTED` | `INITIAL`, `REVALIDATED`, `RESUMPTION_ONLY` | Кирилл явно решил не запускать или не продолжать рассматриваемую редакцию; это окончательный отказ, а не запрос на доработку | В `INITIAL` только при `G25_INITIAL_REJECTION_ONLY` — `REJECTED_BEFORE_EXECUTION`; в `REVALIDATED` или `RESUMPTION_ONLY` после любой прежней полной User Acceptance — `EXPERIMENT_CLOSURE` → `DECISION_UPDATE` |
| `RESUMPTION_CONFIRMED` | Только `RESUMPTION_ONLY` | Подтверждено продолжение неизменённой принятой версии, оставшиеся действия, срок и ресурсы после freshness check | `EXECUTION` той же версии |

Молчание, обсуждение, неоднозначный ответ, реакция без явного смысла, согласие только с частью обязательных предметов или согласие «в целом» не являются ни `USER_ACCEPTED`, ни `RESUMPTION_CONFIRMED`.

`USER_RETURNED` нельзя использовать с disposition `Closure` как замену `USER_REJECTED`. Запрос изменить содержание и окончательное решение не продолжать имеют разные семантику, запись и маршрут.

После прежней полной User Acceptance конечный статус не определяется самим `USER_REJECTED`: после обязательных Experiment Closure и Decision Update применяются обычные правила `CLOSED_COUNTED`/`CLOSED_NOT_COUNTED`. `CLOSED_COUNTED` по-прежнему требует квалифицирующего внешнего действия и выполнения остальных условий зачёта.

### 9.9. Обязательная запись в досье

User Acceptance Gate Record сохраняет:

- режим;
- точную редакцию;
- предъявленный Telegram-summary и его соответствие полной версии;
- применимые результаты двух прежних гейтов;
- отдельные решения по тринадцати предметам раздела 9.5 либо узким предметам `RESUMPTION_ONLY`;
- каждый принятый или непринятый пробел;
- бесплатный пакет и его границы;
- расходы, подтверждённые отдельно от принятия досье;
- передаваемые данные и полномочия;
- результат, дату, владельца и следующий переход;
- отсутствие автоматического согласия на будущие действия и расходы;
- любой User Acceptance carry-forward.

Для первого `USER_ACCEPTED`, разрешающего первый переход в Execution, Gate Record неизменяемо фиксирует `EXPERIMENT_STARTED`, `experiment_started_at`, принятую длительность, плановый deadline и абсолютный deadline не позднее `experiment_started_at + 14 дней`. Для `REVALIDATED` и `RESUMPTION_ONLY` записывается ссылка на исходный старт; новый старт не создаётся.

### 9.10. Возвраты и Cycle Review

User Acceptance не имеет жёсткого числового лимита возвратов. Это не разрешает бессрочную переработку: при любом триггере раздела 23 обязателен Cycle Review. Он обязан развести пользовательский запрос на изменение, отсрочку и окончательный отказ, определить владельца разрешения и не может превратить повторение прежнего согласия или компромисс Кирилла в техническую приёмку.

## 10. User Acceptance / INITIAL

### 10.1. Назначение и границы

`INITIAL` — первая полная пользовательская приёмка редакции, если ни одна редакция кейса ещё не была принята. Она определяет, разрешён ли первый запуск.

Точный вход и проверки соответствуют разделам 9.4–9.7. Кирилл не вправе использовать `INITIAL` для принятия блокирующего дефекта или редакции без двух прежних применимых гейтов.

### 10.2. Условия прохождения

`USER_ACCEPTED` допустим, если:

1. два прежних гейта применимы к точной редакции;
2. Telegram-summary соответствует полной версии;
3. все тринадцать предметов решения приняты однозначно;
4. каждый раскрытый пробел принят отдельно;
5. бесплатный пакет ограничен либо отсутствует;
6. расходы не скрыты в общем согласии;
7. Кирилл понимает остаточную неопределённость и риск;
8. решение выражено явно.

Прохождение `INITIAL` означает немедленное начало нормативного отсчёта эксперимента. Если Кирилл ещё не готов начать отсчёт, допустимый результат — `USER_DEFERRED` и `PAUSED_USER`, а не `USER_ACCEPTED` с более поздней контрактной датой начала.

### 10.3. Условия возврата, отсрочки и отклонения

- `USER_RETURNED` — Кирилл указывает замечания или частичное несогласие и желает переработки.
- `USER_DEFERRED` — Кирилл явно откладывает решение; запуск блокируется.
- `USER_REJECTED` — только окончательный отказ, когда выполнен `G25_INITIAL_REJECTION_ONLY`: режим `INITIAL`, досье ни разу не принималось, внешнего действия нет, отказ окончательный.

Пока не уточнено, является ли ответ запросом на изменение, отсрочкой или окончательным отказом, результат гейта отсутствует. После уточнения фиксируется соответствующий `USER_RETURNED`, `USER_DEFERRED` или `USER_REJECTED`; неоднозначность сама по себе не создаёт ни одного из них.

### 10.4. Условия эскалации

Эскалация нужна, если Кириллу предлагают принять критический/обязательный дефект, неполный обязательный предмет, общий расход или расходящийся summary. Гейт блокируется и возвращается к соответствующему владельцу; согласие Кирилла не исправляет нарушение.

## 11. User Acceptance / REVALIDATED

### 11.1. Назначение

`REVALIDATED` — полная пользовательская приёмка новой редакции после материального изменения уже рассматривавшегося или принятого досье. Она проводится только после повторных Technical Review и System Acceptance этой редакции.

### 11.2. Дополнительный точный вход

Помимо общего входа, Кирилл получает:

- прежнюю принятую редакцию;
- новую редакцию;
- полный delta;
- причину материального изменения;
- какие прежние гейты и полномочия перестали применяться;
- влияние на уже выполненные действия и доказательства;
- остаток 14-дневного срока и ресурсов;
- новый Telegram-summary.

### 11.3. Что принимается

Кирилл заново принимает все тринадцать предметов раздела 9.5 для новой редакции, а не только delta. Сравнение с прежней версией обязательно, но не заменяет полную приёмку.

Прежние фактически выполненные действия и доказательства остаются историей; новая приёмка не делает их задним числом соответствующими изменённому плану.

### 11.4. Условия прохождения

`USER_ACCEPTED` допустим, если новая редакция прошла два повторных гейта, принята полностью, срок не достиг 14 дней и новые полномочия однозначны.

### 11.5. Условия возврата и эскалации

- Явный запрос доработать текущую редакцию или внести материальное изменение даёт `USER_RETURNED` и ведёт в `REWORK_REQUIRED` либо `REVALIDATION_REQUIRED`.
- Временная отсрочка даёт `USER_DEFERRED`.
- Если Кирилл окончательно не разрешает продолжение после любой прежней полной User Acceptance, фиксируется `USER_REJECTED`, после чего кейс идёт в `EXPERIMENT_CLOSURE` → `DECISION_UPDATE`.
- После Decision Update конечный статус определяется обычными правилами `CLOSED_COUNTED`/`CLOSED_NOT_COUNTED`; один факт отказа не отменяет и не создаёт квалифицирующее внешнее действие.
- Попытка сохранить прежний запуск при непринятой материально изменённой версии блокируется.

## 12. User Acceptance / RESUMPTION_ONLY

### 12.1. Назначение и ограничение

`RESUMPTION_ONLY` — узкое пользовательское подтверждение продолжения после review condition без материального изменения. Оно не является полной повторной приёмкой досье, не создаёт новую baseline-версию и не заменяет `REVALIDATED`.

### 12.2. Точный вход

Обязательны:

1. идентификатор кейса и точная ранее принятая редакция;
2. прежний полный User Acceptance;
3. Evidence Record и Review Condition Record;
4. обязательный актуальный Telegram-summary;
5. результат freshness check;
6. доказательство отсутствия материального изменения;
7. оставшиеся внешние действия;
8. остаток срока до принятой границы и до абсолютных 14 дней;
9. остаток нагрузки, количества действий, денег и иных ресурсов;
10. действительность каждого прежнего полномочия, бесплатного пакета и подтверждения данных;
11. новые факты и остаточная неопределённость, не меняющие контракт;
12. открытые обязательства и ожидаемые доказательства.

### 12.3. Обязательный freshness check

Проверяются:

- актуальность предмета решения и прежней принятой редакции;
- актуальность критических внешних фактов;
- отсутствие нового решающего неизвестного или изменения гипотезы;
- состояние success, review и stop conditions;
- отсутствие изменения внешних действий, адресатов, смысла, данных и риска;
- остаток принятого и абсолютного срока;
- остаток нагрузки, количества действий и ресурсов;
- действительность полномочий, бесплатного пакета и отдельных подтверждений;
- отсутствие нового расхода;
- безопасность, обратимость и внешние обязательства;
- применимость прежних правил интерпретации.

### 12.4. Что подтверждает Кирилл

Кирилл явно подтверждает только:

1. продолжение той же принятой редакции;
2. актуальность предмета решения;
3. точный перечень оставшихся действий;
4. оставшийся срок;
5. оставшиеся ресурсы и нагрузку;
6. действительность прежних полномочий и принимаемый остаточный риск.

Новый расход всё равно требует отдельного индивидуального подтверждения и, как изменение расхода, правил материальности.

### 12.5. Условия `RESUMPTION_CONFIRMED`

Результат допустим только если:

1. freshness check завершён;
2. точная принятая версия не изменилась материально;
3. review condition разрешена в пределах прежних правил;
4. день 14 не достигнут;
5. оставшиеся действия, срок и ресурсы определены;
6. прежние полномочия действительны;
7. Кирилл дал явное подтверждение.

### 12.6. Когда `RESUMPTION_ONLY` прекращается

Режим немедленно прекращается и требуется `REVALIDATED`, если:

- обнаружено любое материальное изменение из принятого перечня;
- нематериальность нельзя уверенно доказать;
- требуется новое или изменённое внешнее действие, адресат либо смысл сообщения;
- меняются данные, полномочия, существенный риск, расход, срок за границы или нагрузка сверх лимита;
- меняются гипотеза, решающее неизвестное, условия или правила интерпретации;
- прежние гейты или полная User Acceptance неприменимы;
- Telegram-summary нельзя согласовать с прежней полной редакцией без содержательной правки.

Если день 14 достигнут, `REVALIDATED` также не возобновляет текущий эксперимент: обязательны Evidence Collection, Closure и Decision Update, а продолжение возможно только новым связанным кейсом.

### 12.7. Возврат, отсрочка и эскалация

- `USER_DEFERRED` ведёт в `PAUSED_USER`.
- Явный запрос доработки или материального изменения фиксируется как `USER_RETURNED`; материальная переработка ведёт в `REVALIDATION_REQUIRED` и три гейта.
- Явное окончательное решение не продолжать фиксируется как `USER_REJECTED` и ведёт в `EXPERIMENT_CLOSURE` → `DECISION_UPDATE`.
- Неподтверждение продолжения само по себе, молчание или неоднозначность не являются `USER_REJECTED`; применяются `USER_DEFERRED`/`PAUSED_USER` до явного решения.
- Неясность материальности эскалируется к владельцам затронутых гейтов и до разрешения блокирует Execution.

## 13. USER_DEFERRED и PAUSED_USER

### 13.1. Что сохраняется

При `USER_DEFERRED` и переходе в `PAUSED_USER` сохраняются:

- точная предъявленная редакция;
- режим User Acceptance;
- все прежние Gate Records и carry-forward;
- предъявленный Telegram-summary;
- уже данные явные решения без превращения частичного согласия в полную приёмку;
- непринятые предметы и вопросы к Кириллу;
- причина или условие отсрочки;
- состояние возврата;
- принятый срок эксперимента и абсолютная 14-дневная граница, если эксперимент уже начат.

### 13.2. Что блокируется

До нового явного результата запрещены:

- запуск или возобновление Execution;
- любое новое внешнее действие;
- любой расход;
- передача новых данных;
- расширение пакета, срока, нагрузки или полномочий;
- истолкование ранее принятой части как полного согласия;
- автоматическое закрытие или принятие.

Допускаются только внутреннее сохранение, одно напоминание, freshness check, безопасное закрытие уже существующего обязательства и подготовка ответа без внешнего действия.

### 13.3. Напоминание и таймаут

1. Через 24 часа без блокирующего ответа направляется одно напоминание.
2. Через 72 часа без результата кейс находится в `PAUSED_USER`; молчание не меняет гейт и не создаёт согласие или отказ.
3. Явная отсрочка должна иметь дату либо условие возврата; если Кирилл указал более поздний срок, кейс всё равно остаётся `PAUSED_USER`, а срок служит контрольным моментом, не автоматическим решением.
4. Истечение пользовательского контрольного срока запускает новый запрос решения и freshness check, но не закрытие.

### 13.4. Возврат из паузы

Перед возвратом обязательно проверяются актуальность вопроса, фактов, редакции, срока, рисков, данных, полномочий, расходов и уже принятых подтверждений.

- Если изменений нет и первоначальная/повторная приёмка ещё не завершена, кейс возвращается в тот же режим User Acceptance.
- После review condition без материального изменения используется `RESUMPTION_ONLY`.
- При материальном изменении требуется новая редакция и `REVALIDATED` после двух прежних гейтов.
- При потере актуальности ранее принятого кейса — Closure и Decision Update.

Автоматического согласия нет ни при каком таймауте.

## 14. Carry-forward результатов гейтов

### 14.1. Назначение

`Carry-forward` — явное решение владельца уже пройденного гейта о том, что результат для исходной редакции остаётся применимым к новой редакции при доказанно нематериальном delta без полного повторения этого гейта.

Carry-forward не объединяет редакции, не стирает старый Gate Record, не является новой приёмкой другого гейта и не заменяет `RESUMPTION_ONLY`.

### 14.2. Кто может выдать и для какого гейта

| Гейт | Кто может выдать carry-forward | Что не может выдать этот владелец |
|---|---|---|
| Technical Review | Только Technical Reviewer, владелец применимого результата | System Acceptance или User Acceptance carry-forward |
| System Acceptance | Только System Acceptor, владелец применимого результата | Technical Review или User Acceptance carry-forward |
| User Acceptance | Только Кирилл, владелец исходного пользовательского решения | Technical Review/System Acceptance carry-forward, новый расход, новый пробел или расширение полномочий |

Для цепочки на новой редакции требуется отдельный carry-forward каждого уже пройденного гейта. Перенос позднего гейта не подразумевает перенос раннего.

### 14.3. Обязательные поля carry-forward

Запись содержит:

1. идентификатор кейса;
2. гейт и режим, если применимо;
3. исходную редакцию;
4. целевую редакцию;
5. полный точный delta;
6. затронутые канонические записи и пользовательские представления;
7. проверку по всему перечню материальных изменений;
8. доказательства нематериальности;
9. влияние на критерии гейта и прежние замечания/пробелы;
10. явное утверждение, что результат гейта не изменился бы при проверке целевой редакции;
11. границы переноса и исключения;
12. подтверждение отсутствия новых полномочий, расходов, данных и рисков;
13. владельца и основание его полномочия;
14. дату;
15. следующий разрешённый переход.

### 14.4. Как доказывается нематериальность delta

Нематериальность доказана только если выполнена документированная проверка:

1. delta исчерпывающе перечислен, а не описан как «небольшие правки»;
2. каждая правка сопоставлена с материальными категориями;
3. показано, что правка не меняет предмет, выбор, риск, полномочия, действие, данные, расход, срок, нагрузку, условия, доказательную силу или правила интерпретации;
4. показано, что прежние замечания и пробелы не открываются заново;
5. применён контрфактический тест: если бы Reviewer, Acceptor или Кирилл видел целевую редакцию изначально, его результат и объём решения остались бы теми же;
6. проверено соответствие Telegram-summary и других проекций каноническим записям;
7. владелец гейта явно принимает основание нематериальности.

Одного заявления автора правки, малого объёма текста или отсутствия намерения изменить смысл недостаточно.

### 14.5. Изменения, которые нельзя переносить без повторного гейта

Carry-forward запрещён при изменении:

- основного вопроса, scope или жизненного решения;
- baseline, если изменение меняет точку сравнения;
- гипотезы;
- решающего неизвестного;
- success, review или stop conditions;
- типа внешнего действия;
- адресата или независимой системы;
- смысла, утверждений, обещаний или обязательств внешнего текста;
- передаваемых или используемых данных;
- любого расхода;
- существенного риска;
- срока за ранее принятые границы;
- нагрузки сверх лимита;
- правил интерпретации или качества ожидаемого результата;
- минимально необходимого доказательства или способа подтверждения выполнения;
- безопасности, обратимости или необратимого обязательства;
- полномочий или границ бесплатного пакета;
- критического основания решения;
- категории глубины при появлении обязательного триггера повышенной глубины.

Чисто орфографическая, форматная или ссылочная правка может быть перенесена только если доказано отсутствие изменения человечески воспринимаемого смысла и всех перечисленных последствий.

### 14.6. Сомнение в материальности

Если нематериальность нельзя уверенно подтвердить:

1. delta считается материальным;
2. carry-forward запрещён;
3. затронутые действия блокируются;
4. создаётся новая целостная редакция;
5. выполняются Technical Review → System Acceptance → User Acceptance/REVALIDATED.

### 14.7. Специальный контракт User Acceptance carry-forward

Кирилл может перенести только применимость **собственной** прежней User Acceptance на доказанно нематериальную целевую редакцию. Такой carry-forward дополнительно к разделам 14.3–14.6:

1. указывает исходную и целевую редакции;
2. показывает Кириллу полный delta;
3. содержит его явное подтверждение, что прежнее пользовательское решение полностью остаётся применимым к целевой редакции;
4. не заменяет отдельные Technical Review и System Acceptance carry-forward;
5. не разрешает новый или изменённый расход;
6. не разрешает новое или изменённое действие, адресата, независимую систему либо внешний текст;
7. не расширяет пакет действий, срок, нагрузку, данные, полномочия или границы автономности;
8. не принимает новый риск или новый раскрытый пробел;
9. запрещён при любом изменении человечески воспринимаемого смысла решения.

Если Кирилл не подтвердил перенос явно, User Acceptance для целевой редакции считается отсутствующей. Молчание, показ delta без решения или carry-forward другого гейта не создают пользовательскую приёмку.

## 15. Критерии приёмки и запрет ретроспективного изменения

Запрет ретроспективного изменения критериев в этом разделе выведен из `PLS-022`, `PLS-050` и `PLS-051`; отдельного нового решения журнала он не создаёт.

### 15.1. Что фиксируется до первого внешнего исполнения

До начала Execution в точной принимаемой редакции зафиксированы:

- критерии Technical Review;
- критерии System Acceptance;
- критерии User Acceptance соответствующего режима;
- критерии качества ожидаемого результата;
- условия возврата;
- правила доказательства выполнения каждого действия;
- правила оценки доказательной силы;
- правила интерпретации результата;
- success, review и stop conditions.

### 15.2. После начала Execution

Владельцы гейтов не могут молча:

- повысить или понизить порог прохождения;
- добавить новый обязательный критерий к уже выполненному действию;
- объявить заранее достаточное доказательство недостаточным или наоборот;
- изменить значение success, review, stop или inconclusive;
- изменить условие возврата, чтобы оправдать выбранный исход.

Изменение критерия:

1. сохраняет прежний критерий в истории;
2. создаёт новую редакцию с точным delta и причиной;
3. проходит проверку материальности;
4. при материальности блокирует затронутые действия и требует трёх гейтов;
5. при доказанной нематериальности требует явных carry-forward владельцев уже пройденных гейтов.

Критерий не применяется задним числом к действию или доказательству, полученному до его принятия, если только он не является исправлением явной ошибки безопасности; такое исправление фиксируется отдельно и не переписывает историческую оценку.

## 16. Стандартная структура Gate Record

Каждый Gate Record имеет следующую структуру:

| Поле | Содержание |
|---|---|
| Идентификатор кейса | Стабильная ссылка на один кейс |
| Гейт и режим | `Technical Review`, `System Acceptance` либо `User Acceptance`; для User Acceptance — `INITIAL`, `REVALIDATED` или `RESUMPTION_ONLY` |
| Точная редакция | Единственная редакция, к которой относится результат |
| Входные материалы | Полный перечень рассмотренных канонических записей, представлений, прежних Gate Records и delta |
| Применённые критерии | Версия и полный набор заранее определённых критериев |
| Результат | Один допустимый результат конкретного гейта |
| Замечания или пробелы | Замечания Technical Review, продуктовые несоответствия, раскрытые пробелы либо `нет` |
| Подтверждения | Применимые полномочия и явные решения; для User Acceptance — раздельные решения и расходы |
| Carry-forward | Ссылки на применимые записи переноса либо `не применимо`; сам перенос хранится полностью |
| Дата | Момент вынесения результата и, если важно, дата актуальности входа |
| Активное системное время | Фактическое время этого гейта в составе единого бюджета подготовки либо отдельной пост-acceptance работы; пересечение параллельных интервалов не суммируется дважды |
| Владелец | Technical Reviewer, System Acceptor или Кирилл |
| Следующий разрешённый переход | Ровно один переход либо перечень допустимых путей при возврате/эскалации |

Gate Record неизменяем как историческое решение. Ошибка исправляется новой помеченной записью, которая ссылается на прежнюю и не уничтожает её.

## 17. Разделение полномочий

| Роль | Что определяет | Что не может подменить |
|---|---|---|
| Technical Reviewer | Техническую допустимость, критичность и критерии исправления технических дефектов | Соответствие полного продукта и ценностное решение Кирилла |
| System Acceptor | Соответствие полной редакции продуктовому контракту, допустимость раскрытых пробелов и готовность к пользовательскому решению | Технический pass, пользовательское принятие риска и разрешение на действие |
| Кирилл | Ценностную приемлемость, остаточный риск, личные компромиссы и разрешение на запуск/возобновление | Техническую допустимость, продуктовый контракт и переклассификацию дефекта |

Ни одна роль не может принять собственную работу вместо требуемой независимой проверки. Совпадение технической реализации функций не отменяет раздельных продуктовых решений, критериев и Gate Records.

## 18. Разрешение разногласий между гейтами

### 18.1. Основной порядок

1. Более поздний гейт фиксирует наблюдаемое несоответствие в своём Gate Record.
2. Он указывает затронутое требование, редакцию и ближайший источник возврата.
3. Результат раннего гейта остаётся в истории без переписывания.
4. Исполнение блокируется, если несоответствие влияет на допустимость перехода.
5. Исправление создаёт новую редакцию; применимые гейты повторяются или получают допустимый carry-forward.
6. Если спор касается полномочия раннего гейта, окончательное решение по этому вопросу выносит владелец раннего гейта новой записью, а не поздний гейт.
7. Если спор меняет принятый продуктовый контракт, вопрос эскалируется Кириллу как заказчику; это не даёт ему права принять технический дефект как есть.
8. Если разногласие повторяет прежнюю позицию без новых данных или не даёт содержательного прогресса, проводится Cycle Review по разделу 23; он определяет владельца разрешения, но не переписывает решения гейтов и не создаёт автоматическую приёмку.

### 18.2. Типовые конфликты

| Конфликт | Разрешение |
|---|---|
| System Acceptor видит возможный технический дефект после pass | `RETURNED` по несоответствию; Technical Reviewer повторно оценивает точную редакцию; старый pass не переписывается |
| Кирилл видит техническую проблему | `USER_RETURNED`; дефект направляется к источнику и Reviewer; согласие или несогласие Кирилла не классифицирует дефект |
| Reviewer считает пробел допустимым, Acceptor — запрещённым продуктовым пробелом | System Acceptance возвращает досье; Reviewer сохраняет техническую оценку, но к User Acceptance перехода нет |
| Acceptor считает досье готовым, Кирилл не принимает остаточный риск | `USER_RETURNED`, если Кирилл просит изменить досье; `USER_DEFERRED`, если откладывает решение; `USER_REJECTED`, если явно и окончательно отказывается запускать/продолжать. Только `INITIAL/G25` ведёт прямо в `REJECTED_BEFORE_EXECUTION`; после прежней полной приёмки — Closure → Decision Update. System Acceptance не меняется задним числом |
| Кирилл хочет продолжить с обязательным дефектом | Запрещено; выбирается допустимый путь эскалации либо Closure |

## 19. Инварианты трёх гейтов и запрещённые обходы

| Инвариант | Запрещённый обход | Обязательная реакция |
|---|---|---|
| Каждый результат относится к точной редакции | Показать или исполнить другую редакцию | Блокировать переход; новый гейт или carry-forward |
| Гейты идут `TR → SA → UA` для полной приёмки | Кирилл «заменяет» внутренний гейт согласием | Вернуться к недостающему гейту |
| Technical Review независимо | Автор принимает собственную доказательную конструкцию без независимой проверки | `TECH_REVIEW_RETURNED`; назначить независимую проверку на продуктовом уровне |
| System Acceptance не повторяет и не переписывает TR | Acceptor меняет класс технического дефекта | Записать разногласие и вернуть владельцу TR |
| User Acceptance — ценностное решение | Представить его как оценку качества системы | Переформулировать предмет решения; гейт не завершён |
| `USER_RETURNED` и `USER_REJECTED` различны | Использовать возврат с disposition `Closure` вместо окончательного отказа | Записать фактическое решение: доработка — `USER_RETURNED`; окончательный отказ — `USER_REJECTED` с применимым маршрутом |
| Прямой первоначальный отказ строго ограничен | Направить отказ после прежней полной User Acceptance в `REJECTED_BEFORE_EXECUTION` | `EXPERIMENT_CLOSURE` → `DECISION_UPDATE`; затем обычный конечный статус |
| Критический и обязательный дефекты блокируют | Принять их Кириллом или скрыть как рекомендацию | Возврат/эскалация/Closure |
| Раскрываемые пробелы ограничены | Принять запрещённый пробел через `ACCEPTED_WITH_DISCLOSED_GAPS` | `RETURNED` |
| Каждый пробел принимается поштучно | Общее или частичное согласие | User Acceptance не пройден |
| Каждый расход индивидуален | Вывести расход из согласия на досье или бюджет | Расход заблокирован до отдельного подтверждения |
| Бесплатный пакет имеет закрытые границы | Добавить адресата, данные, смысл, риск или количество | Отдельное подтверждение либо повторные гейты |
| Review останавливает Execution | Вернуться напрямую без User Acceptance | `RESUMPTION_ONLY` либо `REVALIDATED` |
| `RESUMPTION_ONLY` требует неизменности | Использовать после материального изменения | `REVALIDATION_REQUIRED` |
| Пауза не сохраняет актуальность автоматически | Возобновить по старому подтверждению | Freshness check; при изменении revalidation/Closure |
| Молчание не решение | Считать отсутствие ответа согласием или отказом | Напоминание; `PAUSED_USER` через 72 часа |
| Критерии фиксированы до Execution | Изменить критерий под полученный исход | Новая редакция и правила материальности |
| Gate Record исторически неизменяем | Поздний гейт правит ранний результат | Новая связанная запись без удаления истории |
| Счётчик TR принадлежит кейсу | Сбросить два возврата новой редакцией, revalidation, Execution или Cycle Review | Сохранить накопительный счётчик; следующий блокирующий дефект эскалировать |
| Бюджет подготовки един | Исключить Gate Records или умножить 60 минут параллельными работами | Учитывать единый активный интервал; на 60-й минуте приостановить подготовку |
| Старт эксперимента однократен | Назначить позднюю дату в контракте либо сбросить старт повторной приёмкой | Сохранить исходный `experiment_started_at` и абсолютный deadline |
| Cycle Review не является гейтом | Считать повторный разбор автоматической приёмкой или разрешением дефекта | Сохранить блокировку; выбрать допустимый способ разрешения либо Closure |
| Telegram — проекция полной версии | Исполнить содержание summary, расходящееся с каноном | Блокировка; исправление редакции/проекции и применимые гейты |
| День 14 необратим | Возобновить через новый User Acceptance | Evidence → Closure → Decision Update; новый кейс |

## 20. Проверка опасных сценариев

| Сценарий | Почему опасен | Решение контракта |
|---|---|---|
| Technical Review пройдено для `R1`, пользователю показана `R2` | Пользователь решает по непроверенному содержанию | User Acceptance блокируется, пока для `R2` не будет повторного результата либо явного carry-forward каждого применимого прежнего гейта; молчаливый перенос запрещён |
| После Technical Review изменён внешний текст | Может измениться смысл, риск, данные или доказательство | Создаётся новая редакция и точный delta; изменение человечески воспринимаемого смысла, утверждений, адресата или обязательств запрещает carry-forward и требует повторных гейтов |
| System Acceptance пытается принять критичный пробел | Обход технической допустимости и запрещённых категорий | `RETURNED`; `ACCEPTED_WITH_DISCLOSED_GAPS` запрещён. Неоценимые границы или последствия — обязательный/критический дефект |
| Кирилл принимает расход общим согласием на досье | Создаёт скрытое денежное полномочие | Расход остаётся неподтверждённым и блокируется до отдельного решения |
| Кирилл принимает только часть раскрытых пробелов | Остаточный риск не принят полностью | `USER_ACCEPTED` невозможен; `USER_RETURNED` или `USER_DEFERRED` |
| Третий обязательный дефект просто принимается Кириллом | Подменяет Technical Reviewer | После двух Gate Records `TECH_REVIEW_RETURNED` любой открытый критический/обязательный дефект создаёт `THIRD_MANDATORY_DEFECT`; Кирилл выбирает только допустимый путь разрешения либо Closure |
| `RESUMPTION_ONLY` используется после материального изменения | Обходит три повторных гейта | Режим прекращается; `REVALIDATION_REQUIRED` → TR → SA → UA/REVALIDATED |
| Во время `PAUSED_USER` изменились факты или полномочия | Старое согласие стало неприменимым | Freshness check; при материальности — revalidation, при потере актуальности ранее принятого кейса — Closure → Decision Update; автоматического согласия нет |
| Более поздний гейт переписывает ранний результат | Уничтожает происхождение решения | Старый Gate Record сохраняется; поздний гейт возвращает работу и создаёт собственную запись |
| Telegram-summary расходится с полной версией | Пользователь принимает иной объект | User Acceptance блокируется; каноническая версия имеет приоритет; расхождение исправляется с редакцией/carry-forward по влиянию |
| Критерии изменены после начала Execution | Позволяет подогнать оценку под исход | Прежние критерии сохраняются; изменение — новая редакция и проверка материальности, без ретроспективной подмены |
| Одна продуктовая роль принимает собственную работу без независимой проверки | Самоподтверждение скрывает дефект | Такой Gate Record недействителен; требуется независимая проверка соответствующим владельцем |
| Gate Records исключены из 60 минут или параллельным веткам дан отдельный бюджет | Позволяет молча обойти ограничитель подготовки | Гейт без записи не пройден; все параллельные работы используют единый активный интервал, а на 60-й минуте подготовка приостанавливается |
| Новая редакция или Cycle Review сбрасывает счётчик Technical Review | Позволяет бесконечные обычные возвраты | Счётчик живёт весь кейс; после двух возвратов следующий блокирующий дефект вызывает `THIRD_MANDATORY_DEFECT` |
| `REVALIDATED` или `RESUMPTION_ONLY` задаёт новый старт | Позволяет продлить эксперимент сверх 14 дней | Сохраняются исходные `experiment_started_at` и абсолютный deadline; после него новое действие возможно только в новом связанном кейсе |

## 21. Уточнённые решения и аудиторские коррекции v2

1. **Единица лимита Technical Review.** Считаются Gate Records с результатом `TECH_REVIEW_RETURNED`, а не отдельные дефекты. После двух обычных возвратов любой открытый критический или обязательный дефект создаёт `THIRD_MANDATORY_DEFECT`.
2. **Разведение пользовательских исходов.** `USER_RETURNED` означает запрос доработки или материального изменения. `USER_REJECTED` означает явный окончательный отказ запускать или продолжать редакцию. Только `INITIAL` при `G25_INITIAL_REJECTION_ONLY` ведёт прямо в `REJECTED_BEFORE_EXECUTION`; после прежней полной User Acceptance отказ проходит через Closure и Decision Update.
3. **User Acceptance carry-forward.** Кирилл может явно перенести только собственную приёмку на доказанно нематериальную редакцию в границах раздела 14.7. При отсутствии его явного подтверждения User Acceptance новой редакции отсутствует.
4. **Запрещённый пробел и остаточная неопределённость.** Перечень раздела 8.2 утверждён. Известная ограниченная остаточная неопределённость допустима только при описанных источнике, влиянии, границах, мерах снижения и явном принятии Кириллом.
5. **Возвраты System Acceptance и User Acceptance.** Жёсткого числового лимита нет. Зацикливание обязательно обрабатывается через Cycle Review по разделу 23.
6. **Независимость без проектирования реализации.** Документ запрещает самоприёмку содержания, но не определяет число людей, агентов, моделей или вызовов; конкретный механизм реализации остаётся вне этого контракта. Это следствие `PLS-017`, а не отдельное новое решение.
7. **Жизнь счётчика Technical Review.** Счётчик `TECH_REVIEW_RETURNED` действует всю жизнь кейса и сбрасывается только новым связанным кейсом.
8. **Время гейтов и старт эксперимента.** Technical Review, System Acceptance и обязательные Gate Records входят в единый 60-минутный бюджет до предъявления на первый User Acceptance; первый принятый переход в Execution однократно фиксирует `EXPERIMENT_STARTED` и абсолютный deadline.

## 22. Обнаруженные противоречия с предыдущими документами

Содержательных противоречий с синхронизированными документами v2 и решениями `PLS-001–PLS-066` после аудиторской доработки не обнаружено.

Семантика `USER_REJECTED` сохранена из принятой state machine v1 и соответствует `03-state-machine-v2.md`:

- в `INITIAL` при `G25_INITIAL_REJECTION_ONLY` — прямой переход в `REJECTED_BEFORE_EXECUTION`;
- в `REVALIDATED` или `RESUMPTION_ONLY` после любой прежней полной User Acceptance — `EXPERIMENT_CLOSURE` → `DECISION_UPDATE`;
- конечный статус определяется обычными правилами зачёта, а не названием события отказа.

State Machine изменять или синхронизировать по `USER_REJECTED` не требуется.

## 23. Cycle Review и потенциальные циклы возвратов

### 23.1. Назначение и триггеры

Для System Acceptance и User Acceptance не устанавливается жёсткий числовой лимит возвратов. Вместо него **Cycle Review** обязателен, если выполнено хотя бы одно условие:

1. повторяется тот же корневой дефект;
2. новая редакция не даёт содержательного прогресса;
3. роли повторяют прежние позиции без новых данных;
4. возвраты начинают угрожать принятому лимиту подготовки или актуальности кейса.

Cycle Review может применяться и к межгейтовому спору. Он не заменяет числовой лимит Technical Review и не сбрасывает число Gate Records `TECH_REVIEW_RETURNED`.

### 23.2. Обязательное содержание и результат

Cycle Review обязан:

1. показать хронологию возвратов, редакций и решений;
2. установить корневую причину цикла;
3. отделить новый дефект от повторения прежнего;
4. определить владельца разрешения по действующему разделению полномочий;
5. предложить один или несколько допустимых путей: исправление, сужение scope, новые данные, дополнительный конкретный ресурс, принятие Кириллом допустимого пользовательского компромисса либо Closure;
6. зафиксировать выбранный путь, ответственного, ближайшее проверяемое действие и критерий выхода из цикла.

Cycle Review:

- не является новым гейтом и не создаёт автоматическую приёмку;
- не разрешает Кириллу принять критический или обязательный технический дефект;
- не позволяет роли подменить решение владельца другого гейта;
- не продлевает текущий эксперимент сверх абсолютных 14 дней;
- при невозможности содержательного разрешения предлагает Closure, а не бессрочный новый возврат.

### 23.3. Карта потенциальных циклов

| Цикл | Риск | Ограничитель |
|---|---|---|
| Dossier Assembly ↔ Technical Review | Последовательное обнаружение дефектов | Полный список блокирующих замечаний за попытку; два Gate Records `TECH_REVIEW_RETURNED`; затем эскалация |
| Technical Review Escalation ↔ Rework | Повтор тех же исправлений без решения | Выбранный путь, новый ресурс/данные или Closure; Cycle Review не сбрасывает лимит TR |
| Technical Review ↔ System Acceptance | Спор о техническом дефекте или продуктовой полноте | Разделение полномочий; поздний гейт не переписывает ранний; при повторе — Cycle Review |
| System Acceptance ↔ Dossier Assembly | Возврат одного и того же продуктового несоответствия | Единый список, root cause, точный delta; при повторе или отсутствии прогресса — Cycle Review |
| System Acceptance ↔ Technical Review через новую редакцию | Исправление полноты меняет доказательную логику | Проверка материальности; повторный TR либо явный carry-forward; при позиционном споре — Cycle Review |
| User Acceptance ↔ Rework | Частичные изменения без стабилизации решения | Развести `USER_RETURNED`, `USER_DEFERRED`, `USER_REJECTED`; при повторе — Cycle Review и владелец разрешения |
| `PAUSED_USER` ↔ User Acceptance | Бесконечная отсрочка | Одно напоминание, пауза через 72 часа, контрольная дата/условие и freshness check; без автоматического согласия |
| Review Handling ↔ `RESUMPTION_ONLY` ↔ Execution | Скрытое продление слабого эксперимента | Freshness check, отсутствие материального изменения, остаток ресурсов и необратимый день 14 |
| Исправление summary ↔ гейты | Проекция постоянно расходится с каноном | Один источник истины; изменение смысла создаёт редакцию; повтор расхождения запускает Cycle Review |
