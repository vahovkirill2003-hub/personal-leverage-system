# Personal Leverage System
## Product State Machine v2.1: первый Decision-to-Action Workflow

**Статус:** кандидат на пользовательскую приёмку; не принят. До приёмки действует `03-state-machine-v2.md`  
**Дата:** 14 августа 2026  
**Основание:** принятая `03-state-machine-v2.md`; единственное изменение — редакционное уточнение маршрутизации правила `RELEVANCE_LOST` после входа в `EXPERIMENT_PLANNING` (§9) и общая routing policy §9.1  
**Область:** один кейс по одному актуальному карьерно-доходному решению  
**За рамками:** схемы досье и артефактов, программная архитектура, база данных, API, JSON Schema, классы, технические типы, модели, провайдеры и код

## 1. Назначение

State machine определяет текущее продуктовое положение кейса, события, guards, разрешённые и запрещённые переходы, паузы и терминальные исходы. Она предотвращает запуск без приёмки, действия без полномочий, скрытое продолжение после review condition, обход повторных гейтов, закрытие без Decision Update и продление эксперимента сверх 14 дней.

State machine описывает продуктовую логику. Состояние, стадия или роль не означают отдельного агента, вызова модели, сообщения или программного компонента.

## 2. Стадия, состояние, режим и продуктовый статус

| Понятие | Определение | Пример |
|---|---|---|
| Стадия workflow | Логический набор ответственности, работы и гейт. | Technical Review проверяет доказательность и безопасность. |
| Состояние кейса | Единственное текущее положение кейса, определяющее допустимые события и переходы. | `EXECUTION`, `DECISION_UPDATE`. |
| Режим состояния | Уточняет назначение входа в состояние, не создавая новую полную стадию. | `USER_ACCEPTANCE` в режиме `INITIAL` или `RESUMPTION_ONLY`. |
| Продуктовый статус | Крупный пользовательский режим паузы или итог кейса. | `PAUSED_USER`, `CLOSED_COUNTED`. |
| Административный disposition входа | Результат прекращения обработки до Experiment Planning; не состояние и не статус кейса. | `PRE_EXPERIMENT_DISMISSED`. |

В каждый момент у кейса одно состояние. Для `USER_ACCEPTANCE` фиксируется один из режимов:

- `INITIAL` — первоначальная полная приёмка версии досье;
- `REVALIDATED` — полная приёмка версии после материального изменения и повторных Technical Review и System Acceptance;
- `RESUMPTION_ONLY` — узкое подтверждение продолжения после review condition без материального изменения. Кирилл подтверждает продолжение, актуальность той же версии, оставшиеся действия, оставшийся срок и ресурсы. Полная повторная приёмка неизменённого досье не требуется.

## 3. Состояния

### 3.1. Основные активные состояния

| Состояние | Продуктовый смысл | Стадия workflow |
|---|---|---|
| `INTAKE` | Выделить один допустимый актуальный вопрос. | Intake |
| `CLARIFICATION` | Уточнить цель, ставку, альтернативы, ограничения и срок актуальности. | Clarification |
| `FACT_UNKNOWN_MAPPING` | Отделить факты от предположений и определить решающее неизвестное. | Fact and Unknown Mapping |
| `EXPERIMENT_PLANNING` | Связать неизвестное с минимальной внешней проверкой и условиями эксперимента. | Experiment Planning |
| `DOSSIER_ASSEMBLY` | Собрать целостную версию досье. | Dossier Assembly |
| `TECHNICAL_REVIEW` | Независимо проверить текущую версию. | Technical Review |
| `SYSTEM_ACCEPTANCE` | Проверить продуктовый контракт и допустимость пробелов. | System Acceptance |
| `USER_ACCEPTANCE` | Получить первоначальную, повторную либо узкую resumption-приёмку Кирилла. | User Acceptance |
| `EXECUTION` | Выполнять только подтверждённые внешние действия. | Execution |
| `EVIDENCE_COLLECTION` | Зарегистрировать свидетельства и отделить наблюдение от вывода. | Evidence Collection |
| `REVIEW_CONDITION_HANDLING` | Остановить исполнение и выбрать путь после review condition. | Review Condition Handling |
| `EXPERIMENT_CLOSURE` | Необратимо завершить активный эксперимент и свести результат. | Experiment Closure |
| `DECISION_UPDATE` | Зафиксировать следующее решение Кирилла. | Decision Update |

### 3.2. Возвраты и повторные гейты

| Состояние | Назначение | Допустимый выход |
|---|---|---|
| `REWORK_REQUIRED` | Зафиксировать дефект и вернуть к ближайшему источнику. | В `INTAKE`, `CLARIFICATION`, `FACT_UNKNOWN_MAPPING`, `EXPERIMENT_PLANNING` или `DOSSIER_ASSEMBLY`. |
| `REVALIDATION_REQUIRED` | После материального изменения остановить затронутые действия и аннулировать применимость прежних гейтов. | К источнику изменения, затем обязательно через `DOSSIER_ASSEMBLY` и три гейта. |
| `TECHNICAL_REVIEW_ESCALATION` | После третьего обязательного дефекта прекратить автоматические возвраты и потребовать допустимого способа разрешения. | Исправление, сужение, новые данные, дополнительный ресурс, обоснованная переклассификация ревьюером либо Closure. |

### 3.3. Ожидание и пауза

| Состояние | Когда используется | Запрещено |
|---|---|---|
| `PAUSED_USER` | Нет ответа Кирилла 72 часа либо он явно отложил продолжение. | Считать молчание согласием, выполнять действия, тратить деньги или закрывать кейс автоматически. |
| `PAUSED_EXTERNAL` | Продолжение зависит от внешнего ответа или события с контрольным сроком. | Автоматически продлевать эксперимент или ждать без контрольной реакции. |

Через 24 часа ожидания Кирилла допускается одно напоминание; через 72 часа обязателен `PAUSED_USER`. Перед выходом из любой паузы проверяется актуальность.

### 3.4. Терминальные состояния

| Состояние | Смысл | Зачёт пилота |
|---|---|---|
| `CLOSED_COUNTED` | Closure и Decision Update завершены; все условия формального зачёта выполнены. | Да |
| `CLOSED_NOT_COUNTED` | Closure и Decision Update завершены, но хотя бы одно условие зачёта отсутствует. | Нет |
| `REJECTED_BEFORE_EXECUTION` | Досье окончательно отклонено только во время первоначального User Acceptance, ни разу не принималось и внешнего действия не было. | Нет |

Терминальный статус не отменяется и кейс не открывается повторно. Допустимое исключение — запись late evidence без перехода в другое состояние и без ретроспективного пересчёта зачёта.

`PRE_EXPERIMENT_DISMISSED` отсутствует в таблице терминальных состояний намеренно. Он завершает административную обработку входа до Experiment Planning вне продуктового контура терминальных статусов, не является шестым статусом, не требует Closure или Decision Update и не образует завершённый экспериментальный цикл.

## 5. Guards

| Guard | Обязательное условие |
|---|---|
| `G01_SCOPE` | Одно конкретное актуальное решение в домене карьеры и дохода; нет второго активного эксперимента. |
| `G02_CLARIFIED` | Подтверждены цель, ставка, альтернативы, ограничения, срок актуальности и существенные интерпретации. |
| `G03_MAP_READY` | Основания классифицированы; решающее неизвестное определено; актуальные факты имеют источники и даты. |
| `G04_PLAN_READY` | Есть связь «неизвестное → внешнее действие → доказательство → решение», baseline, срок 3–14 дней, лимиты, риски и success/review/stop conditions. |
| `G05_DOSSIER_READY` | Версия целостна; действия, свидетельства, расходы, риски, полномочия и пробелы раскрыты. |
| `G06_TECH_PASSED` | Technical Review пройдено для этой версии; критических и обязательных незакрытых дефектов нет. |
| `G07_SYSTEM_ACCEPTED` | Для этой версии есть `ACCEPTED` или `ACCEPTED_WITH_DISCLOSED_GAPS`; запрещённых пробелов нет. |
| `G08_FULL_USER_ACCEPTED` | Кирилл явно принял текущую версию в режиме `INITIAL` или `REVALIDATED`; каждый раскрытый пробел принят отдельно. |
| `G09_ACTION_AUTHORIZED` | Действие индивидуально подтверждено либо полностью входит в действующий пакет заранее определённых бесплатных действий. |
| `G10_EXPENSE_AUTHORIZED` | Конкретные сумма, назначение и риск расхода индивидуально подтверждены Кириллом. |
| `G11_PACKAGE_IN_BOUNDS` | Тип, количество, адресат/правило выбора, смысл, данные, срок, риск и доказательство остаются в принятом бесплатном пакете. |
| `G12_RESUMPTION_ONLY_ACCEPTED` | После review condition без материального изменения Кирилл явно подтвердил продолжение, актуальность той же версии, оставшиеся действия, срок и ресурсы. |
| `G13_REPEAT_GATES_COMPLETE` | Материально изменённая версия прошла Technical Review, System Acceptance и User Acceptance. |
| `G14_FRESHNESS_CHECKED` | Перед возобновлением проверены актуальность вопроса, версии, фактов, срока, рисков и подтверждений. |
| `G15_EVIDENCE_READY` | Доступные свидетельства зарегистрированы и связаны с действием и решающим неизвестным; пробелы раскрыты. |
| `G16_CLOSURE_COMPLETE` | Действия прекращены; обязательства, время, расходы, доказательства, отклонения, baseline и основание закрытия сведены. |
| `G17_DECISION_UPDATE_COMPLETE` | Кирилл зафиксировал решение, основание, изменение уверенности, ответственного и следующий шаг; допустимая отсрочка имеет пять обязательных параметров. |
| `G18_COUNTED` | Одновременно выполнены все условия раздела 17. |
| `G19_NO_OUTSTANDING_OBLIGATIONS` | Нет неучтённых расходов, действий, обещаний или внешних обязательств. |
| `G20_WITHIN_TIMEBOX` | Текущему эксперименту менее 14 дней и действие находится внутри принятого срока. |
| `G21_REVIEW_RESOLVED` | Причина review, доказательства и остаток ресурсов зафиксированы; выбран один путь. |
| `G22_STOP_JUSTIFIED` | Stop подтверждена данными; для отрицательной ожидаемой ценности указаны новые данные, оставшаяся польза, затраты, риски и основание. |
| `G23_INCONCLUSIVE_COUNTABLE` | Способ проверки был разумным до запуска; выполнено countable external action; недостаточность сигнала честно записана; Closure и Decision Update завершены. |
| `G24_COUNTABLE_EXTERNAL_ACTION` | Действие фактически выполнено; взаимодействует с внешним человеком, организацией или независимой системой; создаёт внешний след либо новое внешнее свидетельство; связано с решающим неизвестным; было подтверждено и зарегистрировано. |
| `G25_INITIAL_REJECTION_ONLY` | Текущий `USER_ACCEPTANCE` имеет режим `INITIAL`; досье ни разу не принималось; нет выполненного внешнего действия; отклонение явно окончательное. |
| `G26_LATE_EVIDENCE_ONLY` | Кейс терминален; ответ относится к нему; запись не создаёт новое действие, обязательство или изменение терминального статуса. |
| `G27_PRE_EXPERIMENT_DISMISSIBLE` | Experiment Planning ещё не начался и выполнено хотя бы одно основание: вход вне домена; нет конкретного актуального решения; разумное Clarification не может сделать его допустимым; актуальность потеряна; Кирилл явно прекратил подготовку. |
| `G28_EXPERIMENT_STARTABLE` | Это первый `USER_ACCEPTED`, который разрешает первый переход данного кейса в `EXECUTION`; `experiment_started_at` ранее не установлен. |

## 6. Действия при входе и выходе

| Состояние | При входе | При выходе |
|---|---|---|
| `INTAKE` | Записать сообщение, время, вопрос и начальный baseline. | Записать scope и актуальность. |
| `CLARIFICATION` | Выделить обязательные вопросы и спорные интерпретации. | Записать цель, ставку, ограничения, срок и исходную уверенность. |
| `FACT_UNKNOWN_MAPPING` | Собрать доступные материалы и даты. | Записать факты, предположения, неизвестные и решающее неизвестное. |
| `EXPERIMENT_PLANNING` | Зафиксировать вопрос проверки, лимиты и приоритеты. | Записать гипотезу, внешние действия, доказательства, срок и три условия. |
| `DOSSIER_ASSEMBLY` | Собрать только актуальные материалы. | Зафиксировать точную версию и раскрытые пробелы. |
| `TECHNICAL_REVIEW` | Зафиксировать версию и независимость ревью. | Записать результат, дефекты, критичность и номер возврата. |
| `SYSTEM_ACCEPTANCE` | Проверить версию, прошедшую Technical Review. | Записать `ACCEPTED`, `ACCEPTED_WITH_DISCLOSED_GAPS` или `RETURNED`. |
| `USER_ACCEPTANCE` | Записать режим; показать точную версию или, для `RESUMPTION_ONLY`, неизменность версии, оставшиеся действия, срок и ресурсы. | Записать явное решение, принятые пробелы, полномочия и применимую версию. |
| `EXECUTION` | Проверить актуальность, срок, лимиты и полномочия. | Остановить будущие действия; записать факт, результат, ресурсы и причину выхода. |
| `EVIDENCE_COLLECTION` | Собрать первичные свидетельства. | Отделить наблюдение от вывода; записать силу, пробелы и сработавшее условие. |
| `REVIEW_CONDITION_HANDLING` | Немедленно остановить будущие внешние действия. | Записать выбор, материальность, срок и следующий шаг. |
| `EXPERIMENT_CLOSURE` | Необратимо прекратить текущий эксперимент и выявить обязательства. | Записать Closure Report, предварительный статус и выполнение guards. |
| `DECISION_UPDATE` | Представить сравнение до/после и альтернативные интерпретации. | Записать решение или допустимую отсрочку; при закрытии — статус. |
| `REWORK_REQUIRED` | Записать дефект, источник и критерий исправления. | Сохранить прежнюю версию и маршрут. |
| `REVALIDATION_REQUIRED` | Остановить затронутые действия и аннулировать применимость прежних гейтов. | Записать точку переработки и обязательные повторные гейты. |
| `TECHNICAL_REVIEW_ESCALATION` | Показать третий дефект, две попытки и допустимые способы разрешения. | Записать выбранный путь; простое принятие дефекта запрещено. |
| `PAUSED_USER` | Записать причину, запрос, напоминание и состояние возврата. | Выполнить freshness check и записать ответ. |
| `PAUSED_EXTERNAL` | Записать зависимость, контрольный срок, 14-дневный предел и состояние возврата. | Записать ответ или таймаут и применимый маршрут. |
| `CLOSED_COUNTED` | Записать выполнение `G18_COUNTED` и сохранение финальной версии. | Выход запрещён; допустима только late-evidence аннотация без смены состояния. |
| `CLOSED_NOT_COUNTED` | Записать причину незачёта и завершённые Closure/Decision Update. | Выход запрещён; допустима только late-evidence аннотация без смены состояния. |
| `REJECTED_BEFORE_EXECUTION` | Записать первоначальную непринятую версию, окончательный отказ и `G25_INITIAL_REJECTION_ONLY`. | Выход запрещён; допустима только late-evidence аннотация без смены состояния. |

Административная запись `PRE_EXPERIMENT_DISMISSED` обязательна и содержит: исходное обращение; дату и время; стадию отклонения; причину; применённое правило scope/актуальности; фактическое системное время; подтверждение Кирилла только если закрытие зависит от его выбора; подтверждение отсутствия внешнего действия, расхода и обязательства; итоговый disposition. Она не создаёт Execution Log, Evidence Register, Closure, Decision Update, показатели «до/после» или терминальный статус кейса.

## 7. Разрешённые переходы: основной контур

| Текущее состояние | Событие | Guard | Следующее состояние | Обязательные записи | Требуется подтверждение Кирилла |
|---|---|---|---|---|---|
| Новый кейс | `CASE_SUBMITTED` | Есть конкретная возможность или решение | `INTAKE` | Сообщение, дата, материалы, baseline | Нет; сообщение запускает Intake, не Execution |
| `INTAKE` | `INTAKE_ACCEPTED` | `G01_SCOPE` | `CLARIFICATION` | Вопрос, scope, актуальность | Да, если вопрос существенно переформулирован |

### 9.1. Routing policy правил с несколькими допустимыми целями

Отдельные правила настоящего документа называют более одной допустимой цели. Такое правило остаётся **одним** правилом: обе цели допустимы, ни одна не удаляется, а выбор между ними детерминирован и выводится из авторитетного контекста кейса, а не из цели, предложенной вызывающей стороной.

Общие требования к правилу с несколькими целями:

1. У правила есть предикат маршрутизации, вычисляемый только по уже зафиксированным записям кейса.
2. Вычисление предиката не создаёт записи состояния и не зависит от текста сообщения, модельного вывода или параметра команды.
3. Вычисленная цель, значение предиката и перечень прочитанных записей входят в обязательные записи перехода.
4. Цель, предложенная вызывающей стороной, не принимается как вход: она может быть только сверена с вычисленной, а расхождение — отказ перехода без частичных эффектов.

Для правила `RELEVANCE_LOST` после входа в `EXPERIMENT_PLANNING` (§9) предикат определяется так:

**«Есть незарегистрированные доступные данные»** истинно тогда и только тогда, когда для текущего эксперимента существует хотя бы одно выполненное внешнее действие либо полученный внешний ответ, для которого в реестре свидетельств нет ни зарегистрированного свидетельства, ни раскрытого пробела.

- предикат истинен → `EVIDENCE_COLLECTION`, далее обязательный `EXPERIMENT_CLOSURE` по §7;
- предикат ложен → `EXPERIMENT_CLOSURE` напрямую.

Оба маршрута ведут к обязательным Experiment Closure и Decision Update (§16) и не изменяют условия зачёта §17. Правило не создаёт нового исхода, не затрагивает административный disposition `PRE_EXPERIMENT_DISMISSED` до входа в Planning (отдельные строки §9) и не изменяет §11.

Правила §8 «дефект маршрутизирован» и «изменение маршрутизировано», а также правило §10.1 «Scope сужен или получены новые данные» перечисляют несколько целей и уже содержат собственный предикат в столбце guard (ближайший источник дефекта, источник изменения, определённая материальность по §15). Настоящая policy применяется к ним без изменения текста их строк.

## 10. Лимиты и 14-дневная граница

### 10.1. Подготовка

Единый лимит считает активное системное время от начала Intake до предъявления пакета на первый User Acceptance. В него входят активные Intake/Clarification, Mapping, проверка внешних фактов, Planning, Assembly, Technical Review, System Acceptance, все исправления и возвраты до первого User Acceptance, обязательные Gate Records, обязательный Telegram-summary и иная необходимая работа. Не входят ожидание ответа Кирилла, его чтение и решение, ожидание внешней стороны, внешние действия Кирилла и работа после первого User Acceptance. Параллельные внутренние работы образуют один общий активный интервал и не создают отдельных лимитов.

На 45-й минуте выполняется мягкий `PREPARATION_BUDGET_CHECK`: оценивается вероятность завершения к 60-й минуте, выбирается минимальная либо необходимая пропорциональная глубина, убираются необязательные улучшения и при необходимости предлагается сужение scope. Обязательные требования и гейты не обходятся. При 60 минутах `PREPARATION_LIMIT_REACHED` приостанавливает работу. Кирилл получает лучший доступный результат, открытые дефекты и пробелы, их влияние, фактическое время и оценку дополнительной работы и выбирает: сузить scope, дать данные, одобрить конкретное дополнительное время, отложить либо закрыть. 60 минут — ограничитель, а не гарантия завершения. До данных двух пилотных циклов жёсткие подлимиты стадий не вводятся; фактическое время каждой стадии записывается отдельно.

| Текущее состояние | Событие | Guard | Следующее состояние | Обязательные записи | Требуется подтверждение Кирилла |
|---|---|---|---|---|---|
| Любое подготовительное состояние до первого `USER_ACCEPTANCE` | `PREPARATION_BUDGET_CHECK` | Учтено 45 минут активной подготовки | То же состояние | Вероятность завершения, выбранная глубина, удалённые улучшения, предлагаемое сужение scope | Нет на проверку; да на изменение scope |
| Любое состояние от `INTAKE` до первого `USER_ACCEPTANCE` | `PREPARATION_LIMIT_REACHED` | Учтено 60 минут подготовки | То же состояние; подготовка приостановлена | Время, лучший вариант, пробелы, влияние и варианты | Нет на остановку; да на дополнительное время |
| Приостановленное подготовительное состояние | `ADDITIONAL_TIME_APPROVED` | Кирилл указал конкретный дополнительный объём времени | То же состояние | Объём, назначение и новый контрольный момент | Да |
| Приостановленное подготовительное состояние | Scope сужен или получены новые данные | Определена материальность | `REWORK_REQUIRED` либо `REVALIDATION_REQUIRED` | Решение, данные, материальность и маршрут | Да |
| Приостановленное состояние до входа в `EXPERIMENT_PLANNING` | `PRE_EXPERIMENT_DISMISSED` по явному прекращению Кирилла | `G27_PRE_EXPERIMENT_DISMISSIBLE` | Административная обработка завершена; новое состояние/статус не создаются | Полная административная запись | Да |
| Приостановленное состояние после входа в `EXPERIMENT_PLANNING` | Кирилл закрывает кейс | Решение явно зафиксировано | `EXPERIMENT_CLOSURE` | Причина, время и отсутствие/наличие действия | Да |

### 10.2. Нагрузка и расходы

При достижении 5 часов внешней нагрузки новые действия приостанавливаются. Превышение лимита — материальное изменение и требует повторных трёх гейтов. Каждый расход подтверждается индивидуально независимо от пакетов.

| Текущее состояние | Событие | Guard | Следующее состояние | Обязательные записи | Требуется подтверждение Кирилла |
|---|---|---|---|---|---|
| `EXECUTION` | `USER_LOAD_LIMIT_REACHED` | Учтено 5 часов внешних действий за неделю | `EXECUTION`; новые действия приостановлены | Нагрузка, остаток плана, польза и варианты | Нет на остановку |
| `EXECUTION` с приостановленной нагрузкой | Кирилл не расширяет лимит | Без превышения план не продолжается | `EVIDENCE_COLLECTION` | Решение, выполненные/пропущенные действия и влияние на сигнал | Да |
| `EXECUTION` с приостановленной нагрузкой | Кирилл одобряет превышение | Дополнительная нагрузка конкретна; изменение материально | `REVALIDATION_REQUIRED` | Объём, основание, риск и подтверждение | Да; затем три гейта |
| `EXECUTION` | `UNAPPROVED_EXPENSE_DETECTED` | `G10_EXPENSE_AUTHORIZED` не выполнен | `EXECUTION`; расход и связанное действие блокированы | Сумма, назначение, отсутствие подтверждения и отмена | Нет на блокировку; да до возможного расхода |

### 10.3. Необратимый предел

`experiment_started_at` устанавливается один раз событием `EXPERIMENT_STARTED` при первом `USER_ACCEPTED`, разрешающем первый переход в Execution. Одновременно неизменяемо фиксируются принятая продолжительность, плановый deadline и абсолютный deadline не позднее `experiment_started_at + 14 дней`. Поле «дата начала» в контракте выводится из этого события и не может задавать более поздний отсчёт. Если Кирилл ещё не готов начать отсчёт, применяется `USER_DEFERRED` → `PAUSED_USER` до полной приёмки.

Подготовка до `EXPERIMENT_STARTED` учитывается в едином 60-минутном бюджете, но не входит в длительность эксперимента.

Достижение абсолютного deadline необратимо завершает текущий эксперимент. `REVALIDATED`, `RESUMPTION_ONLY`, пауза, ожидание, материальная версия, дополнительный ресурс и Cycle Review не сбрасывают `experiment_started_at`, не останавливают часы и не продлевают срок.

| Текущее состояние | Событие | Guard | Следующее состояние | Обязательные записи | Требуется подтверждение Кирилла |
|---|---|---|---|---|---|
| Любое нетерминальное состояние начатого эксперимента, кроме `EVIDENCE_COLLECTION`, `EXPERIMENT_CLOSURE`, `DECISION_UPDATE` | `DAY_14_REACHED` | Наступил абсолютный deadline от неизменяемого `experiment_started_at` | `EVIDENCE_COLLECTION` | Старт и deadline, запрет новых действий, доступные/ожидаемые данные и обязательства | Нет на остановку |
| `EVIDENCE_COLLECTION`, `EXPERIMENT_CLOSURE` или `DECISION_UPDATE` | `DAY_14_REACHED` | Наступил абсолютный deadline | Текущее закрывающее состояние сохраняется; новые внешние действия запрещены | Дата, данные, недостающий сигнал, обязательства и маршрут завершения | Нет |

После Evidence Collection обязательны Closure и Decision Update. Продолжение возможно только в новом связанном кейсе с новой проверкой актуальности, baseline и приёмкой. После абсолютного deadline никакая повторная приёмка не разрешает новое внешнее действие в старом кейсе.

## 11. Запрещённые и опасные переходы

| Текущее состояние | Событие | Guard | Следующее состояние | Обязательные записи | Требуется подтверждение Кирилла |
|---|---|---|---|---|---|
| До `USER_ACCEPTANCE` | Попытка Execution | Нет `G06_TECH_PASSED`, `G07_SYSTEM_ACCEPTED`, `G08_FULL_USER_ACCEPTED` для одной версии | **Запрещено; к недостающему гейту** | Попытка, версия, гейт | Кирилл не заменяет технические гейты |
| `EXECUTION` | Расход без `G10_EXPENSE_AUTHORIZED` | Guard не выполнен | **Запрещено; состояние не меняется** | Расход и отмена | Да, индивидуально |
| `EXECUTION` | Действие вне пакета без `G09_ACTION_AUTHORIZED`/`G11_PACKAGE_IN_BOUNDS` | Guard не выполнен | **Запрещено; запрос подтверждения либо `REVALIDATION_REQUIRED`** | Нарушенная граница | Да |
| `REVIEW_CONDITION_HANDLING` | Прямой возврат в Execution | Нет `G12_RESUMPTION_ONLY_ACCEPTED` | **Запрещено; `USER_ACCEPTANCE/RESUMPTION_ONLY`** | Причина и запрос | Да |
| После гейта | Материальное изменение без `G13_REPEAT_GATES_COMPLETE` | Guard не выполнен | **Запрещено; `REVALIDATION_REQUIRED`** | Изменение и аннулированные гейты | Да для новой версии |
| До `DECISION_UPDATE` | Попытка `CLOSED_NOT_COUNTED` | Нет `G16_CLOSURE_COMPLETE`/`G17_DECISION_UPDATE_COMPLETE` | **Запрещено; Closure → Decision Update** | Недостающие шаги | Да для Decision Update |
| Любое состояние без countable external action | Попытка `CLOSED_COUNTED` | Нет `G24_COUNTABLE_EXTERNAL_ACTION`, следовательно нет `G18_COUNTED` | **Запрещено; после Decision Update только `CLOSED_NOT_COUNTED`** | Отсутствие квалифицирующего действия | Да для Decision Update |
| `PAUSED_USER` или `PAUSED_EXTERNAL` | Возобновление без `G14_FRESHNESS_CHECKED` | Guard не выполнен | **Запрещено; пауза сохраняется** | Попытка и freshness gap | По результату проверки |
| Ожидание Кирилла | Молчание | Не удовлетворяет guard согласия | **Не согласие; через 72 часа только `PAUSED_USER`** | Напоминание и пауза | Нет |
| Любое нетерминальное состояние начатого эксперимента на абсолютном deadline | Попытка продолжить эксперимент или новое внешнее действие | `G20_WITHIN_TIMEBOX` невыполним | **Запрещено; Evidence → Closure → Decision Update** | Дата и запрет продления | Новое решение только в новом кейсе |
| `TECHNICAL_REVIEW_ESCALATION` | Кирилл принимает обязательный дефект как есть | Не является допустимым разрешением | **Запрещено; исправление/сужение/данные/ресурс/Closure либо переклассификация ревьюером** | Дефект и выбранный путь | Кирилл выбирает путь, не отменяет дефект |
| `CLOSED_COUNTED`, `CLOSED_NOT_COUNTED`, `REJECTED_BEFORE_EXECUTION` | Попытка открыть кейс или пересчитать статус | Терминальность необратима | **Запрещено; late evidence либо новый связанный кейс** | Ссылка на старый кейс | Да для нового кейса |

Единственный прямой терминальный переход без Closure и Decision Update — `USER_ACCEPTANCE/INITIAL` → `REJECTED_BEFORE_EXECUTION` при `G25_INITIAL_REJECTION_ONLY`. Во всех остальных случаях `CLOSED_NOT_COUNTED` и `CLOSED_COUNTED` достижимы только из `DECISION_UPDATE`.

## 12. Review condition и stop condition

### 12.1. Review condition

1. Будущие внешние действия немедленно прекращаются.
2. Регистрируются условие, данные, момент, остаток срока и ресурсов.
3. Кирилл выбирает: продолжить неизменённый план, материально перепланировать, ждать, закрыть inconclusive или применить stop.
4. Без материального изменения используется `USER_ACCEPTANCE/RESUMPTION_ONLY`; подтверждаются продолжение, версия, оставшиеся действия, срок и ресурсы.
5. При материальном изменении обязательны `REVALIDATION_REQUIRED` и три повторных гейта.
6. После 14 дней продолжение текущего эксперимента запрещено.

### 12.2. Stop condition

1. Новые действия блокируются, безопасное закрытие обязательств продолжается.
2. Stop и доказательство регистрируются.
3. Для отрицательной ожидаемой ценности обязательны новые данные, оставшаяся польза, затраты, риски и основание.
4. Затем всегда следуют Experiment Closure и Decision Update.
5. Stop до countable external action приводит к `CLOSED_NOT_COUNTED`.
6. Stop после такого действия может привести к `CLOSED_COUNTED` только при выполнении всех остальных условий.

## 13. Потеря актуальности

Актуальность проверяется при Intake, перед запуском, перед действием при изменившихся обстоятельствах, после review condition и при выходе из паузы.

- До входа в Experiment Planning потеря актуальности даёт только административный disposition `PRE_EXPERIMENT_DISMISSED` без Closure, Decision Update и продуктового статуса.
- После входа в Experiment Planning окончательное отклонение именно никогда ранее не принятого досье на `INITIAL` User Acceptance может дать `REJECTED_BEFORE_EXECUTION` при `G25_INITIAL_REJECTION_ONLY`; иное закрытие проходит Closure и Decision Update.
- После любой состоявшейся User Acceptance, даже до первого внешнего действия, потеря актуальности или отзыв запуска проходят через Experiment Closure → Decision Update → `CLOSED_NOT_COUNTED`.
- После внешнего действия потеря актуальности обрабатывается как stop condition; зачёт зависит от `G18_COUNTED`.
- После терминального исхода прежний кейс не открывается.

## 14. Повторный User Acceptance

Полная повторная User Acceptance в режиме `REVALIDATED` обязательна после материального изменения и только после повторных Technical Review и System Acceptance.

После review condition без материального изменения используется режим `RESUMPTION_ONLY`. Это не полная повторная приёмка досье: Кирилл подтверждает продолжение, актуальность неизменённой версии, оставшиеся действия, срок и ресурсы. Если при этой проверке обнаружено материальное изменение, `RESUMPTION_ONLY` прекращается и кейс направляется в `REVALIDATION_REQUIRED`.

Любая User Acceptance относится к точной версии и не отменяет индивидуального подтверждения каждого расхода.

## 15. Материальные изменения

Материальны изменения основного вопроса, гипотезы, решающего неизвестного, success/review/stop conditions, типа действия, адресата, смысла сообщения, данных, расхода, существенного риска, срока за принятые границы, нагрузки сверх лимита или правил интерпретации.

Материальное изменение:

1. переводит кейс в `REVALIDATION_REQUIRED`;
2. блокирует затронутые действия;
3. делает прежние гейты и подтверждения неприменимыми к изменённой части;
4. возвращает кейс к источнику изменения;
5. требует новой целостной версии и Technical Review → System Acceptance → User Acceptance.

Нематериальное уточнение остаётся внутри прежних границ, не меняет риск или ожидаемое доказательство и обязательно журналируется. При сомнении изменение считается материальным.

## 16. Закрытие и late evidence

1. `CLOSED_COUNTED` и `CLOSED_NOT_COUNTED` достижимы только из `DECISION_UPDATE`.
2. `CLOSED_NOT_COUNTED` всегда требует Experiment Closure и Decision Update.
3. Единственное прямое исключение — первоначальный `REJECTED_BEFORE_EXECUTION` при `G25_INITIAL_REJECTION_ONLY`.
4. Отзыв принятого запуска до первого внешнего действия не является rejected: он проходит Closure и Decision Update.
5. Достижение 14 дней необратимо завершает текущий эксперимент.
6. Терминальные состояния не открываются повторно.

### 16.1. Поздний внешний ответ

| Текущее состояние | Событие | Guard | Следующее состояние | Обязательные записи | Требуется подтверждение Кирилла |
|---|---|---|---|---|---|
| `CLOSED_COUNTED`, `CLOSED_NOT_COUNTED` или `REJECTED_BEFORE_EXECUTION` | `LATE_EXTERNAL_RESPONSE_RECEIVED` | `G26_LATE_EVIDENCE_ONLY` | То же терминальное состояние | Новая версия late evidence, источник, дата, связь с кейсом; запрет пересчёта | Нет для регистрации |
| То же | Поздний ответ требует нового решения или действия | Ответ зарегистрирован как late evidence; старый статус неизменен | То же терминальное состояние; отдельно создаётся новый связанный кейс через `CASE_SUBMITTED` | Late evidence, ссылка между кейсами, новый вопрос и новый baseline | Да для запуска нового кейса |

Late evidence не открывает кейс, не меняет терминальный статус и не пересчитывает пилот задним числом.

## 17. Формальное определение CLOSED_COUNTED

`CLOSED_COUNTED` присваивается тогда и только тогда, когда одновременно:

1. На входе было одно конкретное актуальное карьерно-доходное решение.
2. Исполняемая версия прошла Technical Review, System Acceptance и полную User Acceptance.
3. До запуска зафиксированы baseline, срок 3–14 дней, лимиты, доказательства, полномочия и три условия.
4. Выполнено хотя бы одно действие, удовлетворяющее `G24_COUNTABLE_EXTERNAL_ACTION`.
5. Каждое действие было в подтверждённых границах; каждый расход подтверждён индивидуально.
6. Данные и недостаточность данных честно зарегистрированы и связаны с решающим неизвестным.
7. Для inconclusive выполнен `G23_INCONCLUSIVE_COUNTABLE`; невыполнение плана не считается inconclusive.
8. Experiment Closure завершён с основанием, временем, расходами, отклонениями, baseline и закрытыми обязательствами.
9. Decision Update завершён явным решением Кирилла.
10. Финальное досье и журналы сохранены вне Telegram.
11. Нет скрытого продления, неучтённого расхода, неподтверждённого действия или обязательства.

Countable external action обязано быть фактически выполнено, взаимодействовать с внешним человеком, организацией или независимой системой, создать внешний след либо новое внешнее свидетельство, относиться к решающему неизвестному, быть подтверждено и зарегистрировано.

Не считаются внешними действиями для зачёта: чтение страницы, веб-поиск, внутренний анализ, черновик без отправки, обсуждение с ИИ, планирование и намерение действовать.

## 18. Инварианты

1. У сформированного кейса ровно одно текущее состояние; `PRE_EXPERIMENT_DISMISSED` прекращает обработку входа до Experiment Planning и не создаёт кейсового состояния.
2. В кейсе одно решение и не более одного активного эксперимента.
3. Стадия, состояние и роль не равны техническому компоненту.
4. Внешнее действие невозможно без `G09_ACTION_AUTHORIZED`; расход — без `G10_EXPENSE_AUTHORIZED`.
5. Пакет не создаёт денежного полномочия.
6. Первоначальная/повторная полная User Acceptance не предшествует Technical Review и System Acceptance той же версии.
7. Материальное изменение требует трёх повторных гейтов.
8. После review condition Execution невозможен без `RESUMPTION_ONLY` или полной `REVALIDATED` приёмки.
9. Молчание никогда не означает согласия, отказа, принятия риска или закрытия.
10. Пауза не возобновляется без freshness check.
11. `experiment_started_at` устанавливается один раз при `EXPERIMENT_STARTED`, никогда не сбрасывается, а текущий эксперимент никогда не продолжает внешние действия после абсолютного deadline.
12. Success/review/stop conditions не меняются задним числом.
13. Непроверенное предположение не становится фактом.
14. Неисполнение не маскируется как inconclusive.
15. `CLOSED_COUNTED` невозможно без `G24_COUNTABLE_EXTERNAL_ACTION`.
16. `CLOSED_NOT_COUNTED` всегда требует Closure и Decision Update.
17. Единственный прямой терминальный исход — первоначальный `REJECTED_BEFORE_EXECUTION` при `G25_INITIAL_REJECTION_ONLY`.
18. Терминальный статус необратим; late evidence не пересчитывает его.
19. История версий, возвратов, дефектов и подтверждений не стирается.
20. Счётчик `TECH_REVIEW_RETURNED` действует всю жизнь кейса и сбрасывается только новым связанным кейсом; третий обязательный дефект нельзя просто принять, а переклассифицирует только ревьюер с обоснованием.
21. Единое активное время подготовки включает обязательные гейты, Gate Records и summary, не умножается параллельными работами и учитывается отдельно от Execution support, Evidence Collection, Closure и Decision Update.
22. После входа в Experiment Planning `CLOSED_NOT_COUNTED` по-прежнему требует Closure и Decision Update; административный disposition больше недоступен.

## 19. Главный успешный путь

`INTAKE` → `CLARIFICATION` → `FACT_UNKNOWN_MAPPING` → `EXPERIMENT_PLANNING` → `DOSSIER_ASSEMBLY` → `TECHNICAL_REVIEW` → `SYSTEM_ACCEPTANCE` → `USER_ACCEPTANCE/INITIAL` → `USER_ACCEPTED + EXPERIMENT_STARTED` → `EXECUTION` → `EVIDENCE_COLLECTION` → `EXPERIMENT_CLOSURE` → `DECISION_UPDATE` → `CLOSED_COUNTED`.

Путь требует одну принятую версию, хотя бы одно действие по `G24_COUNTABLE_EXTERNAL_ACTION`, честную Evidence Collection, завершённые Closure и Decision Update.

## 20. Минимальные альтернативные пути

1. **Предэкспериментальное прекращение:** из `INTAKE` / `CLARIFICATION` / `FACT_UNKNOWN_MAPPING` до Planning событие фиксирует disposition `PRE_EXPERIMENT_DISMISSED`; обработка входа завершается без следующего состояния и без продуктового статуса.
2. **Первоначальный отказ:** `USER_ACCEPTANCE/INITIAL` → `REJECTED_BEFORE_EXECUTION` только при `G25_INITIAL_REJECTION_ONLY`.
3. **Отзыв принятого запуска:** `EXECUTION` до внешнего действия → `EXPERIMENT_CLOSURE` → `DECISION_UPDATE` → `CLOSED_NOT_COUNTED`.
4. **Review без изменения:** `EXECUTION` → `EVIDENCE_COLLECTION` → `REVIEW_CONDITION_HANDLING` → `USER_ACCEPTANCE/RESUMPTION_ONLY` → `EXECUTION`.
5. **Review с изменением:** `REVIEW_CONDITION_HANDLING` → `REVALIDATION_REQUIRED` → переработка → `TECHNICAL_REVIEW` → `SYSTEM_ACCEPTANCE` → `USER_ACCEPTANCE/REVALIDATED` → `EXECUTION`.
6. **Stop до внешнего действия:** Evidence → Closure → Decision Update → `CLOSED_NOT_COUNTED`.
7. **Третий дефект:** `TECHNICAL_REVIEW` → `TECHNICAL_REVIEW_ESCALATION` → допустимое исправление/сужение/данные/ресурс/Closure либо обоснованная переклассификация ревьюером.
8. **Операционный внешний таймаут:** `PAUSED_EXTERNAL` → `REVIEW_CONDITION_HANDLING`.
9. **Таймаут Decision Update:** `PAUSED_EXTERNAL` или `PAUSED_USER` → `DECISION_UPDATE` с fallback.
10. **14 дней:** любое нетерминальное состояние начатого эксперимента → Evidence → Closure → Decision Update; продолжение только новым связанным кейсом.
11. **Late evidence:** терминальное состояние → то же состояние; при новом решении отдельно создаётся связанный кейс.

## 21. Закрытые спорные переходы v0

1. `REJECTED_BEFORE_EXECUTION` ограничен первоначальной приёмкой никогда не принятого досье.
2. Возобновление неизменённого плана использует `USER_ACCEPTANCE/RESUMPTION_ONLY`, а не полную повторную приёмку.
3. `CLOSED_NOT_COUNTED` без Closure и Decision Update запрещён.
4. День 14 необратимо завершает эксперимент.
5. Late evidence не меняет терминальный кейс и пилотный зачёт.
6. Третий обязательный дефект нельзя принять без разрешения; переклассификация принадлежит ревьюеру.
7. Операционный таймаут и таймаут Decision Update имеют разные возвраты.
8. Countable external action формально отделено от внутренней активности.
9. `PRE_EXPERIMENT_DISMISSED` — административный disposition только до Planning, а не статус кейса; после Planning действуют Closure и Decision Update.
10. Единый лимит подготовки включает оба внутренних гейта, Gate Records и summary, а параллельность не создаёт новый бюджет.
11. `EXPERIMENT_STARTED` однократно привязывает абсолютный deadline к первому принятому переходу в Execution.
12. Счётчик Technical Review живёт весь кейс и обновляется только новым связанным кейсом.

## 22. Возможные недостижимые состояния

- `TECHNICAL_REVIEW_ESCALATION` недостижим, если ревью завершается максимум за два возврата.
- `PAUSED_EXTERNAL` недостижим без внешней зависимости.
- `REJECTED_BEFORE_EXECUTION` недостижим после любой состоявшейся User Acceptance.
- `CLOSED_COUNTED` намеренно недостижим без `G24_COUNTABLE_EXTERNAL_ACTION`, трёх гейтов, Closure и Decision Update.
- `REVALIDATION_REQUIRED` недостижим на полностью неизменном главном пути.

Защитная условная недостижимость допустима. Недостижимость обязательного состояния главного пути при выполненных guards является дефектом спецификации.

## 23. Возможные циклы и ограничители

| Цикл | Риск | Ограничитель |
|---|---|---|
| Уточнение ↔ mapping | Бесконечный анализ | Минимально достаточная ясность и лимит подготовки. |
| Mapping ↔ planning | Поиск идеального сигнала | Одно решающее неизвестное и разумная ex ante проверка. |
| Assembly ↔ Technical Review | Бесконечные возвраты | Два возврата за всю жизнь кейса; новая версия, Execution и Cycle Review счётчик не сбрасывают; следующий блокирующий дефект эскалируется. |
| System Acceptance ↔ rework | Маскировка критичных пробелов | Запрещённые категории пробелов не переклассифицируются. |
| Execution ↔ Evidence | Много действий без знания | Принятые действия, лимит нагрузки, три условия и 14 дней. |
| Review ↔ Execution | Продление слабого эксперимента | `RESUMPTION_ONLY`, повторные гейты при изменении и день 14. |
| Closure ↔ Evidence | Незакрываемый кейс | Только доступное незарегистрированное свидетельство; новых действий нет. |
| Decision Update ↔ пауза | Бесконечная отсрочка | Пять параметров и fallback. |
| Терминальный кейс ↔ late evidence | Скрытое переоткрытие | Только версионная запись; статус и зачёт неизменны. |
